# 수식 맵 압축 (Formula Map Compression)

> 비트 시퀀스를 생성하는 수식들에 번호를 매겨 두고, **맵 번호 하나로 많은 바이트를 대체**하는 새로운 압축 방식.

| 항목 | 내용 |
|---|---|
| 등록일 | 2026-08-26 |
| 상태 | ❌ **원안 기각** (수학적 불가능) / ✅ **올바른 형태를 찾아 실측 완료** |
| 판정 근거 | [01-타당성-검토.md](01-타당성-검토.md) |
| **최종 결론** | **[07-학습사전-실측.md](07-학습사전-실측.md) — 학습 사전으로 gzip 대비 69.3% 절감** |

> **원안의 직관 — "미리 공유된 맵의 번호 하나로 많은 바이트를 커버한다" — 은 처음부터 옳았다.**
> **틀린 것은 맵의 내용을 산술 수식으로 채우려 한 것뿐이다. 맵을 데이터가 채우게 하면 실제로 작동한다.**

---

## 원안

1. 비트를 연속 생성하는 **수식**들을 미리 정해 둔다
2. 수식마다 번호를 매긴 **수식 맵**을 만든다 (비트맵처럼)
3. 데이터를 **맵 번호 하나**로 대체해 전송한다
4. 순서는 바꿔도 되고, 256바이트를 배열처럼 다뤄도 된다
5. → 스트리밍 영상의 초반 256/512바이트가 수식 몇 개로 끝난다

---

## 결론 요약

### ❌ 범용 무손실 압축기로는 불가능하다

이건 구현·최적화·수식 선택으로 우회되는 문제가 아니라 **개수 세기(counting)** 로 증명되는 문제다.

| 근거 | 요지 |
|---|---|
| **커버리지** | 256바이트의 경우의 수는 10^616. 수식을 43억 개 준비해도 커버율 **10^-607** |
| **비둘기집 원리** | 길이 n 미만 출력은 2^n−1가지뿐 → 2^n개 입력을 담을 수 없다. 어떤 입력은 **반드시 커진다** |
| **반복 적용** | 모든 입력이 1비트라도 줄면, 반복해서 모든 파일을 1비트로 만들 수 있다 → 모순 |
| **재배열 비용** | 256개 재배열 방법을 지정하는 데만 `log₂(256!)` ≈ **210바이트** 소요 |
| **탐색 불가** | 짧은 수식이 존재해도 찾는 것은 콜모고로프 복잡도 = **계산 불가능** |

> **10초 자가진단법:** 새 압축 아이디어가 떠오르면 "모든 입력에 대해 줄어드나?"를 묻는다.
> **그렇다면 그 아이디어는 틀렸다.** 예외 없다.

**1분 실증:**
```bash
head -c 10000000 /dev/urandom > random.bin
gzip -9 -k random.bin
ls -l random.bin random.bin.gz    # .gz가 더 크다
```

### ✅ 그런데 직관 자체는 틀리지 않았다

원안의 "수식 맵"에는 이미 정식 명칭이 있다 — **모델**이다. 그리고 "압축 = 모델링"이라는 관점은 **정확히 옳다.** 부호화(산술 부호화)는 이미 이론적 최적에 도달했고, 남은 개선 여지는 전부 모델 쪽에 있다.

틀린 것은 방향이 아니라 **"모든 데이터를 커버해야 한다"는 요구**였다. 이것만 풀면 원안의 구조는 실제로 작동하며, 이미 여러 분야에서 쓰이고 있다.

| 실제 기술 | 원안과의 관계 |
|---|---|
| **VQ / 코드북 / LZ 사전** | "번호 하나가 여러 바이트 대체"를 문자 그대로 구현. 단 맵을 **학습**함 |
| **절차적 생성** (데모신) | 96KB에 3D 게임 전체. "작은 시드 → 많은 바이트"의 순수형 |
| **신경망 예측 + 산술 부호화** | **모델 가중치 = 수식 맵.** 원안에 가장 충실한 현대적 구현 |
| **손실 생성 코덱** | 스트리밍 영상 아이디어의 진짜 답. 비트가 아니라 **지각**을 복원 |

## 핵심 교훈

> **압축은 "모든 것을 줄이는 기술"이 아니라 "무엇을 포기할지 고르는 기술"이다.**
>
> 무손실 압축기는 *드문 데이터가 커지는 것*을 포기하고,
> 손실 압축기는 *지각되지 않는 정보*를 포기한다.
> 원안은 아무것도 포기하지 않으려 했고, 그래서 막혔다.

또 하나, 실패하는 압축 아이디어의 가장 흔한 공통점:

> **절약분은 세고 설명 비용(사이드 인포메이션)은 안 센다.**
> "순서를 바꿔도 된다"가 여기 해당한다 — 바꾸는 건 자유지만, **어떻게 바꿨는지 알려주는 비용**이 210바이트다.

## "수식 하나가 10바이트를 커버하면?" (→ [05번](05-수식-하나가-10바이트.md))

레버리지는 8:1로 나쁘지 않다. 손익분기는 **적중 구간 12.7%**, 30% 절감엔 **43%** 가 필요하다.
실제로 길이 10 이상의 상수·등차 구간을 측정한 결과:

| 파일 | 상수 구간 | **등차 구간** | 손익분기 | gzip |
|---|---:|---:|:-:|---:|
| 로그 / 영어사전 | 0.0% | **0.0%** | ❌ | 9.7% / 29.8% |
| `libc`, `bash`, `libcrypto` | 4.8~8.4% | **0.0%** | ❌ | 39~46% |
| `python3.9` (0 패딩) | 97.1% | **0.0%** | ✅ | 1.9% |

- **"1,2,3,4" 같은 등차수열은 6개 파일 전부에서 0.0%** — 실제 데이터에 거의 존재하지 않는다
- 유일하게 통과한 파일에서도 **gzip이 8.7배 우위** (3,802 vs 33,241바이트)
- 10바이트로 잘게 쪼개면 토큰 수가 25배로 늘어 **오히려 나빠진다** (256바이트 단위 4.4% → 10바이트 단위 16.6%)

> **"토큰 하나가 여러 바이트를 커버한다"는 발상은 정확히 옳고, 그것이 바로 LZ77이다.**
> 원안은 **고정 길이 + 고정 사전 LZ77**이고, gzip은 둘 다 가변이라 구조적 상위집합이다.

## ⭐ 최종 — 원안대로 만들어서 측정했다 (→ [06번](06-가변길이-실제구현.md))

가변 길이 + 탐욕적 확장 + 짧으면 버림. **원안의 설계 그대로 압축기를 구현**했다.

| 파일 | A: 수식만 | **B: 수식 하나 추가** | gzip |
|---|---:|---:|---:|
| `cloud-init.log` | **100.2%** (커짐) | **12.8%** | 9.7% |
| `words` | **100.4%** (커짐) | 54.5% | 30.4% |
| `bash` | 96.2% | 68.2% | 49.9% |
| `python3.9` | 3.4% | 3.0% | 1.9% |

**추가한 수식은 딱 하나 — "이 구간은 앞에서 나온 어느 구간과 같다".** 그것만으로 로그가 100.2% → 12.8%.

| 파일 | 등차·상수 수식 커버 | **참조 수식 커버** | 배율 |
|---|---:|---:|---:|
| `cloud-init.log` | 193 바이트 | **145,940 바이트** | **756배** |
| `words` | 3,019 바이트 | **948,390 바이트** | **314배** |

> **원안의 구조는 옳았다. 틀린 것은 수식의 종류였다.**
> **실제 데이터는 수학적으로 규칙적이지 않다 — 대신 자기 자신을 반복한다.**
> **그래서 가장 강력한 수식은 산술식이 아니라 "아까 그거"이고, 그 이름이 LZ77이다.**

남은 gzip과의 격차는 **엔트로피 부호화(허프만)** — `gzip = LZ77 + 허프만`, `B안 = LZ77 + 고정 비트`.

## ⭐⭐ 최종 답 — "수식 10만 개"의 현실판 (→ [07번](07-학습사전-실측.md))

수식 10만 개를 **데이터에서 학습**시키면 어떻게 되는가. 로그를 476바이트짜리 레코드 307개로 쪼개고,
절반으로 사전을 훈련한 뒤 **학습에 쓰지 않은 나머지 절반**으로 측정했다.

| 방식 | 크기 | 원본 대비 |
|---|---:|---:|
| 원본 | 73,333 | 100.0% |
| gzip -9 (개별) | 38,289 | 52.2% |
| zstd -19 사전 없이 | 36,794 | 50.2% |
| **zstd -19 + 학습 사전** | **11,762** | **16.0%** |

```
사전 도입 효과 : 36,794 → 11,762 바이트  (68.0% 추가 절감)
gzip 대비      : 69.3% 더 작음
레코드 하나    : 476바이트 → gzip 249바이트 → 학습사전 76바이트
```

**왜 되나:** 476바이트 레코드는 LZ77이 참조할 과거가 없다. 30KB 사전이 그 과거를 대신 채워준다.
**한계:** 로그 전체를 통째로 압축하면 gzip이 9.7%로 더 좋다. 사전의 가치는 **작은 파일이라 잃어버린 문맥을 되돌려주는 것**이다 — API 응답, 로그 전송, DB 행, IoT 패킷처럼 한 건씩 보내야 하는 경우.

## 속도 — "압축은 느려도 해제는 빠르게" (→ [08번](08-해제속도-실측.md))

| 레벨 | 압축 시간 | 해제 시간 |
|---|---:|---:|
| `-1` | 34 ms | 15 ms |
| `-19` | **2,667 ms** | **22 ms** |

압축은 78배 느려지는데 해제는 그대로 — **레벨 19에서 압축:해제 = 121배 비대칭.**
원안이 원한 설계는 새로 만들 게 아니라 LZ77 계열이 **이미 달성해 둔 성질**이다.

| 사전 크기 | 압축 결과 | 해제 시간 |
|---|---:|---:|
| 없음 | 50.0% | 26 ms |
| 4KB | 17.5% | 20 ms |
| **32KB** | **11.8%** | 19 ms |
| 63KB | 12.8% ⚠️ | 19 ms |

- **사전을 16배 키워도 해제 시간은 20ms → 19ms.** 해제는 탐색이 없고 "거리 D에서 L바이트 복사"를 실행할 뿐이라, 시간이 **출력 크기에만 비례**한다
- 사전을 쓰면 오히려 **34% 빨라진다** (압축 결과가 작아 읽을 데이터가 줄어듦)
- ⚠️ 다만 **32KB가 최적이고 63KB는 오히려 나빠졌다** — 원안의 "너무 많아지면" 우려는 **속도가 아니라 압축률 축에서 실재한다**

## 실측 요약 (2026-08-26)

"모든 데이터"가 아니라 **"실제 데이터의 30%만 줄이자"** 로 목표를 낮추면 개수 세기 논증에 걸리지 않는다.
그래서 실제 파일로 측정했다. → 상세: [03번](03-실측-수식맵-검증.md)

| 파일 | 수식 적중률 | gzip 결과 |
|---|---:|---:|
| 로그 / 영어사전 (텍스트) | **0.0%** | 원본의 9.7% / 29.8% |
| 일반 바이너리 (`libc`, `bash`) | 1.4 ~ 5.6% | 원본의 39~46% |
| `python3.9` (대부분 0 패딩) | 96.2% | 원본의 1.9% |

- **30% 절감에 필요한 적중률은 약 30%** — 인덱스 비용(11비트)은 사실상 공짜라, 성패는 오직 적중률로 결정된다
- 텍스트·로그에서 적중률 **0%** — 1바이트도 못 줄인다. 반면 gzip은 로그를 **90% 줄인다**
- 적중률 96%인 최상 조건에서조차 **gzip이 2.3배 더 좋았다** (8,716 vs 3,802 바이트)
- **핵심 패턴: 수식이 맞는 곳은 gzip이 이미 공짜로 처리하고, gzip이 진짜 일하는 곳에서는 수식이 0% 맞는다**

> **가장 중요한 교훈: 비교 대상을 "무압축"이 아니라 "gzip"으로 잡아야 한다.**
> 로그의 실제 기준선은 이미 90% 줄어든 gzip 결과다. 그 위에서 다시 30%를 줄여야 의미가 있다.

## "수식만 많으면 되지 않나"에 대한 답 (→ [04번](04-수식은-항상-존재한다.md))

**수식은 항상 존재한다.** 적중률 0.0%였던 영어 사전 파일의 256바이트에 대해서도, 그 256개 숫자를 전부 통과하는 다항식을 실제로 구해서 검증했다.

```
수식이 256바이트를 전부 재현하는가?  ->  True  ✅
수식 저장 비용 : 288바이트
원본 크기      : 256바이트
=> 수식이 원본보다 32바이트 더 크다
```

> **수식이 데이터를 없앤 게 아니라, 데이터가 계수로 자리를 옮겼을 뿐이다.**
> 256개 바이트 → 256개 계수. 하나도 사라지지 않았다.

**그리고 수식을 늘려도 해결되지 않는다.** 수식이 많아지면 적중률은 오르지만 **수식 번호도 같이 길어지고, 정확히 상쇄된다.**

| 절약하려는 양 | 커버 가능한 비율 |
|---|---|
| 1비트 | 50% |
| 1바이트 | 0.39% |
| **614비트 (30%)** | **약 10^-185** |

전체의 30%를 커버하려면 수식이 10^616개 필요한데, 그때 번호 길이가 2046비트라 **절약은 1.74비트(0.08%)** 다.

- 표기 단위(4비트/1바이트/hexa)를 바꿔도 경우의 수는 **2^2048로 동일** — 같은 수의 다른 표기일 뿐
- **압축의 어려움은 "수식을 찾는 것"이 아니라 "원본보다 짧은 수식을 찾는 것"이다**

### 작성하지 않은 문서와 그 이유

`시장분석` / `수익구조` / `매출예측`은 **의도적으로 보류**했다.

원안이 기각된 상태에서 시장·수익을 추정하면 **불가능한 제품의 매출을 예측하는 문서**가 되어 오히려 판단을 흐린다.
[02-대안-설계.md](02-대안-설계.md)의 대안 중 하나를 실제로 추진하기로 결정하면, 그 대안을 대상으로 작성한다.

# 06. 가변 길이 수식 매칭 — 실제로 만들어서 측정

> **원안 (정확히 옮김):**
> 수식 1번이 0~15번 자리까지 맞으면 15바이트를 `(시작, 종료, 인수타입)` 4바이트로 줄인다.
> 다른 수식은 3개만 맞으면 손해니까 버린다. 또 다른 수식이 30개 맞으면 크게 이득이다.
> **"데이터가 잘 맞으면 몇 개 수식으로 20자리 30자리를 한 번에 풀 수 있지 않을까."**
>
> **결론: 설계는 옳다. 실제로 구현해서 측정했다.**
> 그런데 측정 결과가 **가장 중요한 수식이 무엇인지**를 알려준다.

측정일: 2026-08-26 / 대상: idea-aws 서버의 실제 파일

---

## 1. 원안대로 구현했다

[05번](05-수식-하나가-10바이트.md)의 고정 길이와 달리, 이번엔 원안 그대로 **맞는 데까지 최대한 확장**하고 짧으면 버린다.

```
리터럴 런 : [플래그1][길이8][원본 8×L]     =  9 + 8L 비트
수식 토큰 : [플래그1][길이8][증가분8]      = 17 비트   ← 원안의 4바이트보다 넉넉함
```

- 수식 = 등차수열 (`증가분 = 0`이면 상수, `= 1`이면 원안의 1,2,3,4)
- 각 위치에서 **최대 길이까지 탐욕적으로 확장**
- **3바이트 미만이면 버리고** 리터럴로 (17비트 > 3×8비트 이므로 원안의 판단과 정확히 일치)
- 최대 255바이트까지 한 토큰으로

> 원안의 *"3개 정도 맞으면 손해"* 는 계산상 정확하다. 손익분기가 정확히 3바이트다.

## 2. A안 — 수식만 썼을 때

| 파일 | 크기 | **A: 수식만** | gzip |
|---|---:|---:|---:|
| `cloud-init.log` | 150,062 | **100.2%** | 9.7% |
| `words` (영어사전) | 1,000,000 | **100.4%** | 30.4% |
| `bash` | 1,000,000 | **96.2%** | 49.9% |
| `python3.9` | 200,080 | **3.4%** | 1.9% |

### 수식 토큰이 실제로 커버한 양

| 파일 | 수식 토큰 수 | 커버한 바이트 | 비율 |
|---|---:|---:|---:|
| `cloud-init.log` | 1,724개 | 5,362 | **3.6%** |
| `words` | 9,066개 | 27,371 | **2.7%** |
| `bash` | 16,516개 | 93,419 | **9.3%** |
| `python3.9` | 1,296개 | 196,588 | **98.3%** |

### 읽는 법

**로그와 텍스트는 원본보다 커졌다(100.2%, 100.4%).** 수식이 커버한 게 3%도 안 되는데 리터럴 런 헤더 비용을 냈기 때문이다. [01번](01-타당성-검토.md)의 "어떤 입력은 반드시 커진다"가 실제로 나타난 것이다.

`python3.9`는 3.4%로 잘 나왔다. 토큰 1,296개가 196,588바이트를 커버했으니 **토큰 하나당 평균 152바이트**다. 원안이 기대한 "20자리 30자리를 한 번에" 가 실제로 일어났다 — 심지어 그보다 5배 크게. 다만 이건 전부 `0x00` 패딩이고, gzip은 여전히 1.9%로 앞선다.

## 3. B안 — 수식을 **하나만** 추가했을 때

여기가 이 문서의 핵심이다. 수식 목록에 딱 하나를 더 넣었다.

> **추가한 수식: "이 구간은 앞에서 나온 어느 구간과 같다"**
> `[플래그1][길이8][거리16]` = 25비트

| 파일 | A: 수식만 | **B: +참조** | gzip |
|---|---:|---:|---:|
| `cloud-init.log` | 100.2% | **12.8%** | 9.7% |
| `words` | 100.4% | **54.5%** | 30.4% |
| `bash` | 96.2% | **68.2%** | 49.9% |
| `python3.9` | 3.4% | **3.0%** | 1.9% |

### 로그 파일이 100.2% → 12.8%

**수식 하나 추가로 8배가 좋아졌다.** 등차수열·상수를 아무리 늘려도 못 하던 일이다.

### 어느 수식이 일을 했나 — 결정적 내역

| 파일 | 등차·상수 수식이 커버 | **참조 수식이 커버** | 배율 |
|---|---:|---:|---:|
| `cloud-init.log` | 193 바이트 | **145,940 바이트** | **756배** |
| `words` | 3,019 바이트 | **948,390 바이트** | **314배** |
| `bash` | 12,983 바이트 | **719,274 바이트** | **55배** |
| `python3.9` | 194,054 바이트 | 3,681 바이트 | (여기선 수식 우세) |

> **참조 수식 하나가 나머지 모든 수식을 합친 것의 수백 배를 커버한다.**

## 4. 그래서 답은

원안의 질문 — *"데이터가 잘 맞으면 몇 개 수식으로 20자리 30자리를 한 번에 풀 수 있지 않을까"* — 에 대한 답:

### ✅ 그렇다. 실제로 된다.

`cloud-init.log`에서 참조 수식은 **145,940바이트를 커버**했다. 토큰 하나가 평균 수십 바이트씩 처리했다. 원안이 상상한 그림 그대로다.

### ❗ 다만 그 "수식"은 산술식이 아니다

가장 강력한 수식은 `1,2,3,4` 같은 것이 아니라 **"아까 나온 그거랑 같다"** 이다.

로그 파일에는 `2026-08-26 01:5...`, `[DEBUG] util.py[...`가 수백 번 반복된다. 이건 어떤 산술 수식으로도 표현할 수 없지만, **"1,700바이트 전 것과 40바이트 동일"** 이라고는 말할 수 있다.

| | |
|---|---|
| 산술 수식이 잡는 것 | 데이터 **내부의 수학적 규칙** — 실제 파일엔 거의 없음 |
| 참조 수식이 잡는 것 | 데이터의 **반복** — 실제 파일에 아주 많음 |

**실제 데이터는 수학적으로 규칙적이지 않다. 대신 자기 자신을 반복한다.** 이 차이가 756배를 만든다.

### 그리고 그 참조 수식의 이름은 LZ77이다

원안의 설계 — 가변 길이, 탐욕적 확장, 짧으면 버림, `(길이, 파라미터)` 토큰 — 은 **LZ77 인코더의 설계와 정확히 같다.** 1977년에 나왔고 gzip·zstd·zip·PNG가 전부 이걸 쓴다.

> **원안은 압축의 올바른 구조를 스스로 재발명했다.**
> 빠져 있던 것은 구조가 아니라 **"가장 쓸모 있는 수식이 무엇인가"** 하나였다.

## 5. B안이 아직 gzip에 지는 이유

| 파일 | B안 | gzip | 차이 |
|---|---:|---:|---|
| `cloud-init.log` | 12.8% | 9.7% | 3.1%p |
| `words` | 54.5% | 30.4% | 24.1%p |
| `bash` | 68.2% | 49.9% | 18.3%p |

남은 격차의 정체는 **엔트로피 부호화**다.

B안은 모든 토큰에 고정 비트 수를 쓴다 — 길이 필드는 언제나 8비트, 리터럴은 언제나 8비트다. 그런데 실제로는:

- 길이 3~5짜리 매치가 길이 200짜리보다 훨씬 자주 나온다 → **자주 나오는 값에 짧은 코드를 줘야 한다**
- 영어 텍스트에서 `e`는 `q`보다 수십 배 자주 나온다 → 같은 8비트를 쓰는 건 낭비다

gzip은 LZ77 위에 **허프만 부호화**를 얹어 이걸 해결한다. 그래서 `words`에서 24%p 차이가 난다.

```
gzip = LZ77 (반복 제거)  +  허프만 (빈도 반영)
B안  = LZ77 (반복 제거)  +  고정 비트        ← 여기가 빔
```

## 6. 종합

| 질문 | 답 |
|---|---|
| 가변 길이로 최대한 확장하는 게 맞나 | ✅ **맞다.** 고정 길이보다 확실히 우월 |
| 3개면 버리고 30개면 취하는 게 맞나 | ✅ **맞다.** 손익분기가 정확히 3바이트 |
| 몇 개 수식으로 20~30자리를 한 번에 푸나 | ✅ **된다.** 실제로 토큰당 평균 152바이트까지 나옴 |
| 산술 수식(1,2,3,4)만으로 되나 | ❌ 로그·텍스트에서 **원본보다 커진다** (100.2%, 100.4%) |
| 무엇이 빠졌나 | ❗ **"앞에 나온 것과 같다"는 수식.** 혼자서 나머지의 **756배**를 커버 |
| 그 수식의 이름은 | **LZ77** (1977년). gzip·zip·zstd·PNG가 전부 사용 중 |
| gzip에 아직 지는 이유 | 엔트로피 부호화(허프만)가 없어서 |

### 한 문장

> **원안의 구조는 옳았다. 틀린 것은 수식의 종류였다.**
> **실제 데이터는 수학적으로 규칙적이지 않다 — 대신 자기 자신을 반복한다.**
> **그래서 가장 강력한 수식은 산술식이 아니라 "아까 그거"다.**

## 부록 — 구현 핵심

```python
FORMULA_BITS = 17   # [플래그1][길이8][증가분8]
MATCH_BITS   = 25   # [플래그1][길이8][거리16]

while i < n:
    best_len, best_kind, best_gain = 0, None, 0

    # 수식 후보: 등차수열을 최대한 확장 (delta=0 이면 상수)
    flen, _ = arith_runlen(data, i, MAXLEN)
    if flen >= 3:                                   # 3바이트 미만은 손해
        gain = flen * 8 - FORMULA_BITS
        if gain > best_gain:
            best_len, best_kind, best_gain = flen, "formula", gain

    # 참조 후보: 앞에 나온 동일 구간
    for pos in candidates(data, i):
        L = match_length(data, pos, i)
        if L >= 4:
            gain = L * 8 - MATCH_BITS
            if gain > best_gain:
                best_len, best_kind, best_gain = L, "match", gain

    ...  # 이득이 가장 큰 것을 선택, 없으면 리터럴
```

전체 스크립트는 세션 스크래치패드의 `varlen.py`.

## 2. 물리 — Unity 내장 PhysX를 쓰지 않는다

### 왜 못 쓰나

| 문제 | 내용 |
|---|---|
| **구름/미끄럼 전이** | 강체 엔진은 마찰을 근사한다. 당구는 **미끄럼→구름 전이 지점**이 결과를 좌우한다 ([06번](06-입력-파라미터-모델.md) 2절) |
| **사이드스핀과 쿠션** | 수직축 회전이 쿠션 반발각에 주는 영향을 PhysX는 모른다 |
| **적분 오차 누적** | 8쿠션까지 가는 궤적에서 스텝 적분 오차가 다이아몬드 단위 오차로 커진다 |
| **결정론** | 리플레이·온라인 동기화·분석에는 **비트 단위 재현성**이 필요하다 |

> 실제로 당구 게임 개발자들은 **자체 물리를 쓴다.** Unity 표준 물리로 만족스러운 결과가 안 나와
> 직접 엔진을 만든 사례, **"운동 미분방정식을 정확히 푸는 이벤트 기반 당구 물리 엔진"** 사례가 있다.

### 무엇을 쓰나 — 이벤트 기반 해석적 솔버

```
상태: 각 공의 (위치, 속도, 각속도) + 운동 상태(미끄럼 / 구름 / 정지)
      ↓
다음 "이벤트"까지의 시간을 해석적으로 계산
      · 미끄럼 → 구름 전이         t = 2v / (7·μs·g)
      · 정지
      · 공–공 충돌
      · 공–쿠션 충돌
      ↓
가장 이른 이벤트로 점프 (스텝 적분 없음)  →  충돌 처리  →  반복
```

| 이점 | |
|---|---|
| **정확** | 구간마다 닫힌 해. 적분 오차 없음 |
| **결정론** | 같은 입력 → 같은 결과. 리플레이·온라인·분석이 성립 |
| **빠름** | 이벤트 수만큼만 계산. 궤적 예측(감도표)을 실시간으로 여러 개 돌릴 수 있음 |

### 참고 구현·문헌

| 출처 | 쓸 곳 |
|---|---|
| [pooltool 이론 문서](https://ekiefl.github.io/2020/04/24/pooltool-theory/) | 방정식 → 코드 전환이 문서화됨. **솔버 골격** |
| [tailuge/billiards](https://github.com/tailuge/billiards) | 백스핀·사이드스핀·쿠션 반발 모델링 참고 |
| **Han (2005), "Dynamics in carom and three cushion billiards"** | **캐롬 쿠션 모델.** 순간성·쿠션 변형 무시 가정의 해석적 모델 |
| [Mathavan · Jackson · Parkin (2010)](https://journals.sagepub.com/doi/10.1243/09544062JMES1964) | 쿠션 충돌 동역학 이론 해석 |

⚠️ **Unity의 역할은 렌더링·입력·씬이지 물리가 아니다.** 물리는 `FixedUpdate`와 분리된 자체 타임라인에서 돈다.

## 3. 1인칭 조준 시퀀스 — 원안의 핵심

**당구의 실력은 치는 순간이 아니라 치기 전 30초에 있다.** 그 30초를 게임 단계로 만든다.

```
① 관찰      테이블을 돌며 배치를 본다          자유 이동, 1인칭
② 각 재기   큐를 들어 라인을 겨눈다            ⭐ 큐를 눈앞에 세워 겨냥선 확인
③ 자리잡기  스탠스·시선 정렬                   위치·발 방향 확정 → 시야가 낮아짐
④ 두께 확인 낮게 앉아 수구–적구 겹침을 본다     ⭐ 카메라가 공 높이까지 내려감
⑤ 당점 조준 큐팁을 수구 어디에 댈지            근접 뷰, 상하·좌우 미세 조정
⑥ 스트로크  백스윙 → 임팩트                    ⭐ 드래그 동작으로 판정
```

### ② 큐로 각 재기

현실에서 하는 동작 그대로 — **큐를 들어 수구와 목표를 잇는 선에 맞춰 본다.**

| 요소 | 구현 |
|---|---|
| 큐를 눈앞에 세움 | 큐 모델을 화면 중앙에 오버레이, 시선 방향으로 정렬 |
| **읽히는 것** | 큐 축의 연장선이 쿠션 어디에 닿는지 — **다이아몬드 눈금과 겹쳐 보인다** |
| 보조 강도 | 기본: 선을 그리지 않고 **큐의 실루엣만**. 보조 켜면 연장선 표시 (기록 분리) |

> **이 단계가 [감도 데모](mockup/)의 "1쿠션 조준점" 슬라이더를 몸동작으로 바꾼 것이다.**

### ④ 낮게 앉아 두께 확인

**두께는 숫자가 아니라 겹침으로 보인다.** 카메라를 공 높이로 내리면 수구와 1적구가 겹쳐 보이고,
그 겹침 비율이 곧 두께다 — [06번](06-입력-파라미터-모델.md) 1절의 `f`.

| 두께 | 화면에서 |
|---|---|
| 8/8 (정면) | 두 공이 완전히 겹침 |
| **4/8 (반두께)** | **적구의 절반이 가려짐** → 절단각 30° |
| 1/8 | 가장자리만 스침 → 절단각 61° |

> **8단계 눈금은 UI가 아니라 시각적 겹침으로 제공하고, 확정 후에만 숫자를 보여준다.**
> 얇은 쪽이 각도 변화가 1.7배 크므로 ([06번](06-입력-파라미터-모델.md) 1절) **카메라 감도를 두께에 따라 비선형으로** 준다.

### ⑥ 스트로크 판정 — 백스윙에서 읽는다

원안: *"손으로 뒤로 뺐다가 치는 걸 판단해서 밀어치기·끌어치기·보통치기 등"*

**드래그 궤적 하나에서 4개 물리 파라미터를 뽑는다.**

| 드래그에서 읽는 것 | 물리 파라미터 | 근거 |
|---|---|---|
| **뒤로 뺀 거리** | 큐 속도 `v` | 백스윙이 길수록 세게 |
| **미는 속도 / 가속 곡선** | `v` 미세 조정 + 스트로크 성격 | 잽 vs 롱 팔로우 |
| **팔로우스루 길이** (임팩트 후 계속 미는지) | 세로 타점 보정 → **밀어치기** | 끝까지 밀면 톱스핀 |
| **드래그 직전 큐 각도** | 큐 세운 각도 → **커브 성분** | [07번](07-거리-속도-마찰-모델.md) 2절 |

```
짧게 빼고 툭 끊음          →  잽 · 스턴에 가까움
길게 빼고 끝까지 밀어냄     →  밀어치기 · 오버스핀
길게 빼고 빠르게           →  세게치기 · 미끄럼 구간 길어짐 → 스쿼트가 그대로 남음
하단 당점 + 끊어 침        →  끌어치기
```

> **스트로크 타입을 메뉴에서 고르게 하면 안 된다.** [06번](06-입력-파라미터-모델.md) 2절에서 확인한 대로
> **스트로크는 독립 변수가 아니라 (v, 타점, 큐 각도)의 결과**다. 동작에서 그 값들을 읽어야 물리와 일관된다.

⚠️ **강약은 원안대로 드래그(슬라이더) 조작.** 다만 **드래그 거리 → 속도 매핑을 비선형으로** 해야 한다 —
미끄럼 전이 거리가 `v²`에 비례하므로 ([06번](06-입력-파라미터-모델.md) 2절), 선형 매핑이면 약한 구간이 뭉개진다.

## 4. ⭐ 장비 시스템 — 스탯을 지어내지 않는다

### 큐 = 자연 피벗 길이

| 큐 등급 | 피벗 길이 | 성격 |
|---|---:|---|
| 입문 목재 | 9.5" | 스쿼트 큼. **예측 가능하고 일정** — 보정량은 크지만 부호가 안 바뀜 |
| 중급 | 13" | 중간 |
| 저디플렉션 | 19" | 스쿼트 작음. **느린 롱샷에서 회전 준 쪽으로 과보정** |

**[07번](07-거리-속도-마찰-모델.md) 3절 계산 그대로** (2팁 · 큐각도 3° · μ=0.20 · 거리 2m, 순 이탈 mm):

| 큐 | v=1.5 | v=2.5 | v=3.5 | v=4.5 | v=5.5 |
|---|---:|---:|---:|---:|---:|
| 목재 9.5" | 39.8 | 44.6 | 51.7 | 67.4 | 72.5 |
| 중급 13" | 17.5 | 22.2 | 29.4 | 45.1 | 50.2 |
| **저디플렉션 19"** | **−1.7** | 3.1 | 10.3 | 25.9 | 31.1 |

> ### **"더 좋은 큐"가 없다. 대역마다 유리한 큐가 다르다.**
> **pay-to-win이 밸런싱이 아니라 물리 때문에 구조적으로 불가능하다.**

### 나머지 장비도 실제 파라미터

| 아이템 | 물리 파라미터 | 게임에서의 효과 |
|---|---|---|
| **팁 (연질/중질/경질)** | 미스큐 한계 오프셋, 팁-공 마찰 | 경질=회전 최대치↑ 대신 미스큐 여유↓ |
| **초크** | 팁 마찰 | 소모품. 안 바르면 미스큐 확률↑ |
| **천 (라사)** | `μs` `μr` | 빠른 대/느린 대. **미끄럼 전이 거리가 바뀜** |
| **쿠션** | 반발 곡선 | 짧게/길게 튀는 대 |
| **공** | 질량·반발 | 대회구 vs 연습구 |

> **튜닝의 목표가 "수치를 올리는 것"이 아니라 "내 스트로크 대역에 맞추는 것"이 된다.**
> 세게 치는 사람과 살살 치는 사람의 최적 세팅이 다르다 — **물리가 그렇게 만든다.**

## 5. 분석 계층 — 앞의 작업이 여기 들어간다

매 샷이 끝나면 [감도 데모](mockup/)가 **리플레이 화면**으로 나온다.

```
[샷 리플레이]
  조준선(기하) ─── vs ─── 실제 궤적        ← 괴리를 눈으로
  ├ 두께 오차       −0.6/8 (얇게 맞음)
  ├ 스쿼트          +41mm  (당신 큐 13", 2팁, 1.8m)
  ├ 커브            −18mm
  └ 스트로크        의도 '보통' → 실제 3.9 m/s (세게치기 대역)
```

| 화면 | 출처 |
|---|---|
| 팁 감도표 | [감도 데모](mockup/) |
| 스쿼트/커브 분해 | [07번](07-거리-속도-마찰-모델.md) |
| **누적 습관 진단** — "3팁 이상에서 항상 짧다" | [08번](08-AX-설계.md) 3절 ③ |
| AI 코치 해설 | [08번](08-AX-설계.md) 3절 ② |
| 다이아몬드 시스템 튜토리얼 | [02-설계](02-설계.md) 2절 |

> **1인칭 정밀 조준은 어렵고, 어려우면 그만둔다. 분석 계층이 그 이탈을 막는 장치다** —
> "왜 빗나갔는지 모르겠다"가 아니라 **"2팁에서 41mm 밀렸다"** 로 끝나야 다시 친다.

### ⭐ 실제 당구대와 맞추기

게임에만 있을 수 있는 기능 하나 — **[07번](07-거리-속도-마찰-모델.md) 8절의 캘리브레이션 5개를 게임에 입력하면,
게임 속 대가 당신이 다니는 당구장 대가 된다.**

> **"집에서 연습한 게 실제 대에서 그대로 통한다."** 이게 다른 당구 게임이 할 수 없는 약속이다.
> 그리고 이건 [04-수익구조](04-수익구조.md) 4절의 **테이블 보정 DB**를 게임이 수집하게 만든다.

## 6. 플랫폼 — 여기에 트레이드오프가 있다

| 플랫폼 | 장점 | 문제 |
|---|---|---|
| **PC (Steam)** | 마우스로 정밀 조준 가능. 3Cushion Masters·Shooterspool의 자리 | 3쿠션 PC 게임 시장이 작다는 것이 이미 관측됨 |
| **모바일** | 한국 당구 인구가 모바일에 있음 | **1인칭 정밀 조준을 터치로 하기 어렵다.** 원안 조작이 가장 죽는 곳 |
| **VR** | **원안 조작 목록이 사실상 VR 설계다** — 자리잡기·시선·백스윙이 전부 자연스러움 | 시장이 가장 작다. [ForeVR Pool](https://store.steampowered.com/app/2363140/ForeVR_Pool_VR/)·[Sports Bar VR](https://store.steampowered.com/app/269170/Sports_Bar_VR/)이 있으나 **포켓볼이고 조준 보조 + 손목 스냅** |

> **원안의 "자리잡고, 시선 처리하고, 낮게 앉아 두께 보고, 손으로 뒤로 뺐다 친다"는 VR에서 자연스럽고 평면에서 어색하다.**
> 평면에서 하려면 **각 단계를 별개 화면 모드로 나누는 설계**가 필요하다 (3절이 그렇게 되어 있다).
>
> **권고: PC 먼저.** 마우스가 정밀 조준에 맞고, 3절 시퀀스를 그대로 구현할 수 있으며,
> VR 이식이 나중에 가능한 구조가 된다. **모바일은 조준 보조를 켠 별개 모드로만.**

## 7. 개발 순서 — 리스크가 큰 것부터

| 단계 | 만드는 것 | 답을 얻는 질문 | 기간 |
|:-:|---|---|---|
| **P1** | **물리 솔버만.** 씬 없음, 공 3개, 스쿼트·커브·마찰 3종·쿠션 | **정확하게 만들 수 있는가** — 실제 당구대 결과와 대조 | 2~4주 |
| **P2** | **조준 시퀀스만.** 3절 6단계, 물리는 P1 | **정확한 게 재미있는가** — 아니면 지루한가 | 2~4주 |
| P3 | 장비 시스템 (4절) + 리플레이 분석 (5절) | 물리 기반 장비가 게임으로 성립하는가 | 6~8주 |
| P4 | 콘텐츠·진행·온라인 | — | 6개월+ |

> **P1과 P2가 이 프로젝트의 두 리스크 전부다.**
> **둘 다 한 달이면 답이 나오고, 하나라도 아니면 1~2년을 아낀다.** ([09번](09-게임화-검토.md) 6절)

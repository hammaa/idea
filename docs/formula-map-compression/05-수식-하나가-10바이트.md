# 05. 수식 하나가 10바이트를 커버한다면?

> **질문:** 수식 하나가 연속된 숫자를 나열한다면 — 예를 들어 1,2,3,4 순서대로 —
> 그래서 수식 하나가 10개를 출력할 수 있다면 어떤가?
>
> **답:** 계산상 **레버리지는 충분하다(8:1)**. 문제는 **그런 구간이 실제 데이터에 거의 없다**는 것,
> 그리고 **gzip이 이미 같은 일을 훨씬 유연하게 하고 있다**는 것이다.

측정일: 2026-08-26 / 대상: idea-aws 서버의 실제 파일

---

## 1. 손익분기 계산

수식 1000개(번호 10비트)가 10바이트(80비트)를 커버하는 구조:

```
적중 구간    : [플래그 1비트][번호 10비트]  =  11비트  →  10바이트(80비트) 대체
미적중 바이트 : [플래그 1비트][바이트 8비트] =   9비트  →   1바이트(8비트)  대체
```

적중 구간에 들어가는 바이트 비율을 `h`라 하면, 전체 `N`바이트에 대해:

```
총 크기 = (11 × hN/10) + (9 × (1−h)N)
        = 1.1hN + 9N − 9hN
        = 9N − 7.9hN

원본 = 8N

본전  : 9 − 7.9h = 8   →  h = 12.7%
30%절감: 9 − 7.9h = 5.6 →  h = 43%
```

| 목표 | 필요한 적중 구간 비율 |
|---|---|
| 손해 안 보기 | **12.7% 이상** |
| 30% 절감 | **43% 이상** |

**레버리지 자체는 나쁘지 않다.** 11비트로 80비트를 대체하니 적중 구간에서는 86% 절약이다. 관건은 오직 **그런 구간이 실제로 얼마나 있는가**이다.

## 3. 가장 중요한 발견 — 등차수열은 모든 파일에서 0.0%

> **원안이 예로 든 "1,2,3,4 순서대로"는 6개 파일 전부에서 단 0.0%였다.**

이건 반올림이 아니라 **실제로 거의 존재하지 않는다**는 뜻이다. 이유는 생각해보면 자명하다.

| 데이터 | 왜 등차수열이 없나 |
|---|---|
| 텍스트·로그 | 글자 코드가 `m,b,i,e`처럼 튄다. 연속 증가할 이유가 없다 |
| 실행 파일 | 명령어 코드와 주소가 섞여 있다 |
| 압축·암호화 데이터 | 설계상 규칙성이 제거되어 있다 |

등차수열이 실제로 나오는 곳은 **인덱스 테이블, 카운터, 이미지의 그라데이션** 정도인데, 전체에서 차지하는 비중이 극히 작다.

### 유일하게 통과한 파일의 정체

`python3.9`만 97.1%로 통과했는데, 내역은 **전부 `0x00` 패딩의 상수 구간**이다. 등차 구간은 여기서도 0.0%다.

그리고 이 파일에서 실제로 붙여보면:

```
수식 방식:
  적중 194,278바이트 → 19,428개 토큰 × 11비트 = 213,708비트
  미적중  5,802바이트 ×  9비트              =  52,218비트
  합계 = 265,926비트 = 33,241바이트 (원본의 16.6%)

gzip -9 = 3,802바이트 (원본의 1.9%)
```

> **수식 방식이 유일하게 손익분기를 통과한 파일에서조차 gzip이 8.7배 더 좋다.**

---

## 4. 왜 10바이트 단위가 오히려 불리한가

여기서 [03번](03-실측-수식맵-검증.md)의 256바이트 실험과 비교하면 중요한 트레이드오프가 보인다.

| 수식 하나가 커버하는 크기 | 커버 구간에서의 효율 | 적중률 |
|---|---|---|
| 10바이트 | 11비트 / 80비트 = **86% 절약** | 상대적으로 높음 |
| 256바이트 | 11비트 / 2048비트 = **99.5% 절약** | 훨씬 낮음 |

**커버 단위가 클수록 토큰당 효율은 좋지만 적중률이 떨어지고, 작을수록 반대다.**

같은 `python3.9`에 대해:
- 256바이트 단위: **4.4%** (토큰 781개)
- 10바이트 단위: **16.6%** (토큰 19,428개)

10바이트로 잘게 쪼개면 **토큰 수가 25배로 늘어나 오히려 나빠졌다.** 고정 길이를 쓰는 한 이 딜레마에서 벗어날 수 없다.

---

## 5. 그런데 이 딜레마는 이미 풀려 있다 — 가변 길이

**gzip(LZ77)이 하는 일이 정확히 원안과 같은 구조다.** 다만 길이가 고정이 아니다.

```
원안  : [번호 10비트]  →  항상 10바이트 (고정)
LZ77 : [길이][거리]    →  3 ~ 258바이트 (가변, 매번 최적 선택)
```

| | 원안의 수식 맵 | LZ77 (gzip) |
|---|---|---|
| 토큰이 커버하는 길이 | **고정** 10바이트 | **가변** 3~258바이트 |
| 참조 대상 | 미리 정한 수식 1000개 | **파일 안에 앞서 나온 모든 내용** |
| `0x00` 19만 바이트 | 토큰 19,428개 필요 | 몇 개의 긴 매치로 끝 |
| 로그의 `"2026-08-26 01:5"` 반복 | 수식에 없음 → 못 잡음 | **잡음** |

**원안의 발상은 LZ77의 특수한 경우(고정 길이 + 고정 사전)다.** 그리고 두 제약을 모두 푼 것이 gzip이라, 구조적으로 이길 수 없다.

> 로그 파일이 90% 줄어드는 이유는 타임스탬프와 모듈명이 수백 번 반복되기 때문인데,
> 이건 어떤 고정 수식으로도 미리 준비할 수 없다. **그 파일을 읽어야만 알 수 있다.**

## 6. 결론

| 질문 | 답 |
|---|---|
| 수식 하나가 10바이트를 커버하면 이득인가 | ✅ 레버리지는 8:1. **원리적으로는 이득** |
| 얼마나 적중해야 하나 | 본전 12.7%, 30% 절감엔 **43%** |
| 실제 적중률은 | ❌ 텍스트·로그 **0.0%**, 바이너리 **4.8~8.4%** |
| "1,2,3,4" 같은 등차수열은 | ❌ **6개 파일 전부 0.0%.** 실제 데이터에 거의 없다 |
| 통과한 파일에서는 이겼나 | ❌ 유일 통과 파일에서도 **gzip이 8.7배 우위** |
| 10바이트로 쪼개면 나아지나 | ❌ 토큰 수가 25배로 늘어 **오히려 나빠졌다** (4.4% → 16.6%) |
| 근본 이유 | 원안 = **고정 길이 + 고정 사전 LZ77**. gzip은 둘 다 가변이라 상위집합 |

### 한 문장

> **"토큰 하나가 여러 바이트를 커버한다"는 발상은 정확히 옳고, 그것이 바로 LZ77이다.**
> **다만 길이를 고정하고 사전을 미리 정하는 순간, 이미 있는 것의 열화판이 된다.**

## 부록 — 측정 코드

```python
MINRUN = 10
def formula_coverage(data):
    """delta가 일정한 최대 구간 중 길이 10 이상인 바이트 수"""
    n = len(data); const = arith = 0; i = 0
    while i < n - 1:
        d = (data[i+1] - data[i]) % 256
        j = i + 1
        while j < n - 1 and (data[j+1] - data[j]) % 256 == d:
            j += 1
        runlen = j - i + 1
        if runlen >= MINRUN:
            if d == 0: const += runlen
            else:      arith += runlen
        i = j
    return const, arith
```

전체 스크립트는 세션 스크래치패드의 `runscan.py`.

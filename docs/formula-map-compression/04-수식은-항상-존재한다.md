# 04. 수식은 항상 존재한다 — 문제는 수식을 적는 비용

> **질문:** "문자열도 숫자로 표기되니까, 1바이트나 4비트 단위로 끊어서 숫자를 만들고 수식으로 풀면 되지 않나?
> 수식만 많으면 될 것 같은데."
>
> **답:** 수식은 **항상 존재한다.** 그런데 **수식을 적어두는 비용이 원본보다 크다.**
> 그리고 "수식을 많이 만드는 것"은 이 문제를 해결하지 못한다 — **수식 번호가 같이 길어지기 때문**이다.

---

## 1. "문자열도 숫자다" — 맞다, 이미 그렇게 다뤘다

먼저 확인. [03번](03-실측-수식맵-검증.md)의 측정은 **텍스트를 텍스트로 다루지 않았다.** 모든 파일을 바이트 정수(0~255)의 나열로 읽고, 그 위에서 상수·등차수열·주기를 판정했다.

```python
d = (b[1] - b[0]) % 256                 # 바이트를 숫자로 빼고 있음
if all((b[i+1] - b[i]) % 256 == d ...)  # 순수 산술 연산
```

압축기 입장에서 **텍스트와 바이너리의 구분은 애초에 없다.** 전부 숫자다. 영어 사전 파일의 적중률이 0.0%였던 것도 "글자라서"가 아니라, **그 숫자열이 단순 수식을 따르지 않아서**다.

---

## 2. 단위를 바꿔도 경우의 수는 변하지 않는다

*"1byte, 또는 4bit 단위로 끊어서"* 부분을 따로 본다.

256바이트를 어떻게 끊어 읽든, **같은 하나의 수를 다른 표기법으로 적는 것**일 뿐이다.

| 읽는 단위 | 항목 수 | 항목당 가능한 값 | 전체 경우의 수 |
|---|---:|---:|---|
| 4비트 (니블/hexa) | 512 | 16 | 16^512 = **2^2048** |
| 8비트 (바이트) | 256 | 256 | 256^256 = **2^2048** |
| 32비트 (4바이트) | 64 | 2^32 | (2^32)^64 = **2^2048** |
| 전체를 하나의 수로 | 1 | 2^2048 | **2^2048** |

**전부 같다.** 10진수를 16진수로 바꿔 적는다고 수가 작아지지 않는 것과 같은 이치다.

> 표기를 바꾸는 것은 정보량을 바꾸지 않는다. 끊는 단위는 **알고리즘 설계의 편의**일 뿐,
> [01번](01-타당성-검토.md)의 개수 세기에는 아무 영향이 없다.

---

## 3. 실증 — 임의의 256바이트를 지나는 수식은 항상 존재한다

여기가 흥미로운 지점이다. **직관은 옳다. 수식은 정말로 항상 찾을 수 있다.**

수학적 사실: **n개의 점을 지나는 n−1차 다항식은 반드시 존재하고, 유일하다.**

그래서 실제로 해봤다. 영어 사전 파일에서 256바이트를 떼어내(= [03번](03-실측-수식맵-검증.md)에서 적중률 **0.0%** 였던 바로 그 파일), 그 256개 숫자를 전부 통과하는 다항식을 구했다.

```
원본 블록 : 256바이트
내용      : b'mbie\nAbercromby\nAberdare\naberdavine\nAber'

수식이 256바이트를 전부 재현하는가?  ->  True   ✅
```

**성공했다.** 단순 수식으로는 0% 적중이던 데이터에 대해서도, 다항식이라는 수식은 **100% 존재한다.**

### 그런데 비용은

```
--- 비용 계산 ---
계수 개수      : 256개 (0이 아닌 계수 255개)
계수 1개당     : 9비트 (값 범위 0~256)
수식 저장 비용 : 2,304비트 = 288바이트
원본 크기      : 2,048비트 = 256바이트

=> 수식이 원본보다 32바이트 더 크다 (112.5%)
```

### **핵심: 수식이 데이터를 없앤 게 아니라, 데이터가 계수로 자리를 옮겼을 뿐이다.**

256개의 바이트가 256개의 계수가 되었다. 하나도 사라지지 않았다. 오히려 계수의 값 범위가 넓어져(0~256) **9비트씩 필요해지는 바람에 12.5% 커졌다.**

> 이것이 "수식으로 풀면 된다"는 발상의 정확한 귀결이다.
> **수식을 찾는 것은 쉽다. 어려운 것은 원본보다 짧은 수식을 찾는 것이다.**

---

## 4. "수식만 많으면 된다"의 정확한 계산

이제 원안의 마지막 보루를 계산한다. 수식을 아주 많이 만들면 어떻게 되는가.

### 상충 관계

| 수식을 늘리면 | 효과 |
|---|---|
| 적중률(커버리지) | ✅ **올라간다** |
| 수식 번호의 길이 | ❌ **같이 길어진다** |

수식이 `F`개면 번호는 `log₂(F)` 비트가 필요하다. **이 둘은 서로 상쇄된다.** 얼마나 정확히 상쇄되는지 계산해 보자.

### 계산

2048비트 블록을 `k`비트 절약해서 `2048−k`비트로 보낸다고 하자.

```
길이 (2048−k)비트로 표현 가능한 서로 다른 값의 수 = 2^(2048−k)
전체 블록 수                                    = 2^2048

커버 가능 비율 = 2^(2048−k) / 2^2048 = 2^(−k)
```

### **정리: k비트를 절약하려면 커버리지가 2^(−k)로 떨어진다.**

이 관계는 **수식의 종류와 무관하다.** 다항식이든 삼각함수든 프랙탈이든 상관없다. 출력의 개수만 세면 나오는 결과이기 때문이다.

### 수치

| 절약하려는 양 | 필요한 수식 개수 | 커버 가능한 비율 |
|---|---|---|
| 1비트 (0.05%) | 2^2047 | 50% |
| 1바이트 (0.4%) | 2^2040 | 0.39% |
| 10바이트 (3.9%) | 2^1968 | 10^-25 |
| **614비트 (30%)** | 2^1434 | **약 10^-185** |
| 절반 (50%) | 2^1024 | 약 10^-308 |

### 뒤집어서 — 수식 개수를 기준으로

원안의 목표대로 **전체의 30%를 커버**하려면 수식이 몇 개 필요한가.

```
F = 0.3 × 2^2048 ≈ 10^616 개

이때 번호의 길이 = log₂(0.3 × 2^2048) = 2048 − 1.74 = 2046.26 비트
절약 = 2048 − 2046.26 = 1.74 비트
```

> **수식을 10^616개 준비해서 얻는 절약은 1.74비트다. 원본의 0.08%.**
>
> 30%를 커버하는 데 성공했는데도 30%가 아니라 0.08%가 나온다.
> **커버리지와 번호 길이가 같은 것**이기 때문이다.

---

## 5. 그렇다면 gzip은 어떻게 로그를 90% 줄이는가

위 계산대로면 어떤 압축도 불가능해야 한다. 그런데 [03번](03-실측-수식맵-검증.md)에서 gzip은 로그 파일을 **90.3%** 줄였다. 모순 아닌가?

모순이 아니다. **위 계산은 "모든 가능한 블록"을 균등하게 가정한 것**이다.

```
전체 블록 공간 (2^2048 ≈ 10^616 가지)
┌──────────────────────────────────────────────┐
│                                              │
│                                              │
│         대부분: 실제로는 절대 등장하지 않음      │
│                                              │
│              ┌───┐                           │
│              │ ● │ ← 실제 로그 파일의 블록들     │
│              └───┘   극도로 좁은 영역에 밀집     │
└──────────────────────────────────────────────┘
```

실제 로그 블록은 `2026-08-26 01:5...`, `[DEBUG] util.py...` 같은 것들이고, 이들은 10^616 공간에서 **상상할 수 없이 좁은 구석**에만 모여 있다. gzip은 전체 공간의 30%를 커버하는 게 아니라, **실제로 등장하는 소수의 블록에만 짧은 번호를 몰아준다.**

### 그래서 진짜 필요한 것

| 필요 없는 것 | 필요한 것 |
|---|---|
| ❌ 수식을 많이 만드는 것 | ✅ **어떤 블록이 실제로 자주 나오는지 아는 것** |

그리고 "무엇이 자주 나오는지"는 **데이터마다 다르다.** 로그 파일의 빈출 패턴과 실행 파일의 빈출 패턴은 전혀 다르다. 미리 정해둘 수 없고, **데이터를 봐야만 알 수 있다.**

- gzip/zstd: 압축하면서 **그 파일에서 실시간으로 학습**
- `zstd --train`: 샘플 데이터로 **미리 학습**해서 사전으로 배포

> **원안이 "미리 정한 수식 맵"으로 하려 했던 일의 올바른 형태가 바로 후자다.**
> 맵을 손으로 정하는 게 아니라 **데이터에서 학습**한다는 것만 다르다. → [03번](03-실측-수식맵-검증.md) 7절

## 6. 종합

| 질문 | 답 |
|---|---|
| 문자열도 숫자니까 수식으로 되지 않나 | ✅ 맞다. 이미 숫자로 다뤘고, 텍스트/바이너리 구분은 없다 |
| 4비트/1바이트로 끊으면 달라지나 | ❌ 표기만 바뀔 뿐 경우의 수는 **2^2048로 동일** |
| 그 숫자를 만족하는 수식이 있나 | ✅ **항상 있다.** 다항식으로 실증 완료 |
| 그럼 압축되나 | ❌ 수식이 **288바이트**. 원본 256바이트보다 크다 |
| 수식을 많이 만들면 되나 | ❌ 커버리지↑ = 번호 길이↑. **정확히 상쇄된다** |
| 30% 커버하는 수식 맵을 만들면 | ❌ 수식 10^616개 필요, 절약은 **1.74비트(0.08%)** |
| 그럼 압축은 왜 되나 | ✅ 실제 데이터가 공간의 극히 일부에만 밀집하기 때문 |
| 무엇을 해야 하나 | ✅ 수식을 늘리는 게 아니라 **데이터에서 빈출 패턴을 학습** (`zstd --train`) |

### 한 문장

> **압축의 어려움은 "수식을 찾는 것"이 아니라 "원본보다 짧은 수식을 찾는 것"이며,**
> **짧은 수식은 데이터에 실제로 구조가 있을 때만 존재한다. 수식 개수를 늘려서 만들어낼 수 없다.**

## 부록 — 재현 코드

```python
P = 257  # 바이트값 0~255를 담으려면 256보다 큰 소수

def newton_coeffs(y):
    """x=0,1,...,n-1 을 지나는 다항식의 뉴턴 계수 (mod P)"""
    n = len(y); c = list(y)
    for j in range(1, n):
        for i in range(n-1, j-1, -1):
            c[i] = (c[i] - c[i-1]) * pow(j, P-2, P) % P
    return c

def evaluate(c, x):
    acc, term = 0, 1
    for i, ci in enumerate(c):
        acc = (acc + ci * term) % P
        term = term * (x - i) % P
    return acc

data = open('/usr/share/dict/words','rb').read()[4096:4096+256]
c = newton_coeffs(list(data))
assert all(evaluate(c, x) == data[x] for x in range(256))   # 통과
print(len(c) * 9 / 8, "바이트 vs 원본", len(data), "바이트")  # 288.0 vs 256
```

전체 스크립트는 세션 스크래치패드의 `polyfit.py`.

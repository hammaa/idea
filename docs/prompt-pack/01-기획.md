# 01. 기획

## 1. 문제 정의

LLM은 "여행 일정 짜줘"에 답할 수 있다. 그런데 **쓸 만한 일정**을 얻으려면 사용자가 다음을 스스로 알아내야 한다.

1. **무엇을 먼저 물어야 하는가** (숙박 도시 순서 → 구간 교통 → 예약 시점)
2. **어떤 제약을 미리 못 박아야 하는가** (귀국 항공편 시각, 체크인/체크아웃, 버스 운행 요일)
3. **어떤 검증을 시켜야 하는가** ("이 일정에서 놓치는 막차 있는지 확인해")
4. **결과를 어떻게 보관할 것인가** (채팅 스크롤 ≠ 예약 체크리스트)

이 4가지가 **프롬프트 설계 노하우**이고, 일반 사용자는 이걸 시행착오로 배운다. 삿포로 케이스에서 그 비용은 **2주**였다.

### 문제의 성질

- 재사용 가능하다 → 한 번 정제한 프롬프트 체인은 다음 사용자에게 그대로 작동
- 도메인 특이적이다 → "일본 자유여행"과 "이직 준비"는 완전히 다른 체인
- 결과물이 문서다 → HTML/PDF로 떨어질 때 가치가 완성됨

## 2. 타깃

### 1차 타깃 (여행 버티컬)

| 세그먼트 | 특징 | 지불 의사 |
|---|---|---|
| **일본 자유여행 초·중급자** | 패키지는 싫고 자유여행은 부담. 온천/렌트카/광역이동이 끼면 특히 막힘 | 높음 — 이미 가이드북·유료 블로그 결제 경험 |
| ChatGPT는 쓰지만 프롬프트는 못 짜는 층 | "그냥 물어보면 그럴싸한데 실제로 안 맞음"을 경험 | 중간 |
| 시간 없는 직장인 | 일정 짜는 시간 자체가 비용 | 높음 |

### 2차 타깃 (확장 시)

- 여행 블로거/인플루언서 — 자기 팔로워용 일정 생성 도구 (화이트라벨)
- 소규모 여행사 — 상담 초안 자동화

### 명확히 제외

- 패키지 여행 선호층 (애초에 일정을 안 짬)
- 프롬프트를 이미 잘 쓰는 파워 유저 (직접 함, 지불 안 함)

---

## 3. 핵심 가치 제안

> **"2주 걸리던 일정 설계를 10분으로. 그리고 채팅이 아니라 문서로 받는다."**

경쟁 대안 대비:

| 대안 | 한계 | 우리의 차별점 |
|---|---|---|
| ChatGPT 직접 사용 | 프롬프트를 직접 설계해야 함, 결과가 안 남음 | 체인이 이미 완성, 산출물이 HTML |
| 여행 블로그/카페 | 남의 일정, 내 항공편·인원에 안 맞음 | 내 제약 기준으로 생성 |
| 여행사 상담 | 비쌈, 자유도 낮음 | 저렴, 자유여행 그대로 |
| 마이리얼트립 등 OTA | 상품 판매가 목적, 일정 설계 도구 아님 | 설계 자체가 상품 |
| 무료 프롬프트 모음집 | 복붙해도 체인/검증이 없음 | 실행까지 포함 |

## 4. 제품 범위

### 팩(Pack)이란

하나의 팩 = **입력 스키마 + 프롬프트 체인 + 산출물 템플릿** 의 묶음.

예: `일본 자유여행 일정 설계 팩`
- 입력: 도시, 날짜, 인원, 왕복 항공편 시각, 예산대, 이동 선호, 필수 방문지
- 체인: 5단계 (→ [02-설계.md](02-설계.md))
- 산출물: 일정표 HTML, 예약 체크리스트, 구간 이동 카드

### 초기 팩 라인업 (가설)

| 우선 | 팩 | 근거 |
|:-:|---|---|
| 1 | 일본 자유여행 일정 설계 | 직접 겪은 문제, 검증 데이터 있음 |
| 2 | 온천/료칸 끼는 일정 (동선 난이도 높음) | 1번의 심화, 가장 아픈 지점 |
| 3 | 렌트카 자유여행 (홋카이도/규슈) | 구간 검증 가치가 큼 |
| 4 | 항공/숙소 예약 타이밍 플래너 | 재방문 유도용 |

**여행 외 확장 후보** (검증 후): 이직 준비, 부동산 임장 체크, 결혼 준비, 개인 사업 인허가.

## 5. MVP 정의

> **가설:** "정제된 프롬프트 체인 + HTML 산출물"에 사람들이 돈을 낸다.

### v0 — 수동 검증 (2~3주)

- 랜딩 페이지 1장 + 신청 폼(구글폼)
- **사람이 직접** 프롬프트 체인을 돌려서 HTML 결과물을 만들어 이메일 발송
- 가격: ₩9,900 (또는 무료 → 후불 "얼마면 낼래?" 조사)
- 목표: **유료 전환 10건**. 안 되면 접거나 피벗.

이 단계에서 개발은 하지 않는다. 삿포로 일정 산출물 하나를 샘플로 공개하는 게 핵심 마케팅 자산.

### v1 — 자동화 (v0 검증 시)

- 웹앱: 폼 입력 → 체인 자동 실행 → HTML 산출물 + 공유 링크
- 결제 연동 (토스페이먼츠/스트라이프)
- 팩 2~3종

### v2 — 마켓플레이스

- 외부 크리에이터가 팩을 등록하고 수익 배분
- 이 단계에서 비로소 "프롬프트 서비스"가 아니라 **플랫폼**

## 6. 성공/실패 판정 기준

| 시점 | 지표 | 기준 |
|---|---|---|
| v0 종료 | 유료 전환 | 10건 이상 → v1 진행 |
| v0 종료 | 산출물 만족도 | "그대로 예약에 썼다" 응답 60% 이상 |
| v1 3개월 | 재사용률 | 1인당 평균 생성 1.5회 이상 |
| v1 6개월 | CAC < LTV | 미달 시 B2B/화이트라벨로 피벗 |

## 7. 명시한 가정

이 문서는 아직 사용자 인터뷰 없이 **본인 경험 1건**을 근거로 작성했다. 다음은 검증되지 않은 가정이다.

1. 삿포로에서 겪은 2주는 일반적인 경험이다 (본인만의 문제가 아니다)
2. 사람들은 일정 설계에 1만 원 내외를 지불할 의사가 있다
3. HTML 산출물이 채팅 답변보다 유의미하게 더 가치 있다
4. 여행 재구매 주기(연 1~2회)에도 사업이 성립한다 ← **가장 약한 가정**

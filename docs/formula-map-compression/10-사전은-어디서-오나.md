# 10. 사전은 압축 대상에서 뽑는 건가 — 정직한 회계

> **질문:** 이 패턴도 압축 대상 파일을 읽어서 미리 잡아 두는 거야?
>
> **답: 아니다. 압축할 파일이 아니라 *다른* 샘플에서 뽑고, 미리 양쪽에 배포해 둔다.**
> 압축 대상에서 뽑으면 사전을 **같이 보내야 하고**, 그 순간 이득의 대부분이 사라진다.
> 실측으로 확인했다.

측정일: 2026-08-26

---

## 1. 왜 이 구분이 결정적인가

[01번](01-타당성-검토.md) 4절에서 정리한 원칙이 그대로 적용된다.

> **"어떻게 복원할지"를 알려주는 정보도 데이터다.**
> 새 압축 아이디어가 실패하는 가장 흔한 지점 — **절약분은 세고 설명 비용은 안 세는 것.**

사전도 데이터다. 문제는 **그 비용을 누가 언제 내느냐**이다.

```
사전을 압축 대상에서 뽑으면  →  받는 쪽이 그 사전을 모른다  →  같이 보내야 한다  →  비용 발생
사전을 다른 샘플에서 뽑으면  →  미리 배포해 둘 수 있다      →  전송할 때 안 보낸다  →  공짜
```

**[07번](07-학습사전-실측.md)의 실측이 정직했던 이유**: 레코드 307개를 절반으로 갈라 **153개로 학습하고, 학습에 쓰지 않은 154개로만 평가**했다. 사전이 외운 걸 되뱉는 게 아니라 처음 보는 데이터에도 통하는지 본 것이다.

---

## 2. 실측 — 4가지 회계 방식 비교

평가셋: 918개 레코드, 443,641바이트 (평균 483바이트). 학습셋과 완전히 분리.

| 방식 | 압축본 | +사전 | 원본 대비 |
|---|---:|---:|---:|
| 사전 없음 | 220,429 | — | **49.7%** |
| ① 다른 샘플로 학습 (사전 미포함) | 55,586 | — | **12.5%** |
| ① 다른 샘플로 학습 (사전 1회 포함) | 55,586 | 88,354 | **19.9%** |
| ② **대상 자신으로 학습** (사전 반드시 동봉) | 49,948 | 82,716 | **18.6%** |

*(사전 크기: 양쪽 모두 32,768바이트)*

---

## 3. 결과 해석 — 세 가지 발견

### 발견 1. 대상 자신으로 학습해도 거의 이득이 없다

```
다른 샘플로 학습 + 사전 동봉 : 19.9%
대상 자신으로 학습 + 사전 동봉 : 18.6%    ← 겨우 1.3%p 차이
```

압축할 데이터를 직접 보고 사전을 만들었는데도 **거의 나아지지 않았다.**

**이유:** 사전에 담은 패턴은 압축본에도 어차피 들어 있다. **같은 정보를 두 번 보내는 셈**이라 사전을 잘 만들수록 압축본이 줄지만, 그만큼 사전이 커진다. 서로 상쇄된다.

> 이건 [04번](04-수식은-항상-존재한다.md)의 "커버리지↑ = 번호 길이↑, 정확히 상쇄"와 같은 현상이다.

### 발견 2. 진짜 이득은 "사전이 이미 저쪽에 있다"에서 나온다

```
12.5%  (사전 미포함)  vs  19.9%  (사전 1회 포함)
```

**7.4%p 차이가 전부 "사전을 안 보내도 된다"에서 나온다.** 사전의 가치는 잘 만드는 데 있는 게 아니라 **미리 가 있다는 사실**에 있다.

### 발견 3. 그래도 사전은 여전히 이긴다

사전 비용을 전부 물려도 **19.9% < 49.7%** 다. 918건에 32KB를 나눠 쓰면 이미 남는다.

---

## 4. 손익분기 — 몇 건부터 이득인가

```
레코드당 사전 없음 : 240.1 바이트
레코드당 사전 사용 :  60.6 바이트
레코드당 절약      : 179.6 바이트
사전 크기          : 32,768 바이트

손익분기 = 32,768 ÷ 179.6 ≈ 182건
```

| 압축 건수 | 사전 없음 | 사전 + 압축본 | 판정 |
|---:|---:|---:|:-:|
| 10 | 2,401 | 33,374 | ❌ 손해 |
| 50 | 12,006 | 35,796 | ❌ 손해 |
| 100 | 24,012 | 38,823 | ❌ 손해 |
| **182** | 43,702 | 43,788 | ⚖️ 본전 |
| 500 | 120,059 | 63,044 | ✅ 이득 |
| 2,000 | 480,237 | 153,870 | ✅ 이득 |
| 10,000 | 2,401,187 | **638,280** | ✅ 이득 |

### 읽는 법

> **사전은 "한 번 내고 무한히 쓰는 고정비"다.**
> 10건 압축하려고 32KB 사전을 만드는 건 명백한 손해다.
> 1만 건이면 사전 비용이 건당 3.3바이트로 희석되고, 전체가 **2.4MB → 638KB**가 된다.

---

## 5. 그래서 사전은 어떻게 운영하나

| 단계 | 내용 |
|---|---|
| 1. 샘플 수집 | 앞으로 압축할 것과 **같은 종류**의 데이터 수백~수천 건 |
| 2. 학습 | `zstd --train` — 여기서만 대상 데이터를 본다 |
| 3. **배포** | 사전을 송·수신 **양쪽에 미리 설치**. 앱 바이너리 내장, 클라이언트 프리로드 등 |
| 4. 사용 | 이후 전송에는 압축본만. 사전 ID로 어느 사전인지 표시 |
| 5. 관리 | 데이터 포맷이 바뀌면 재학습 → **버전 번호를 붙여 관리** |

### 실제 사례가 정확히 이 구조다

| 사례 | 사전을 미리 배포하는 방법 |
|---|---|
| **Brotli** | 웹 상용 문자열 120KB 사전을 **표준에 내장** → 모든 브라우저가 이미 갖고 있음 |
| **zstd 사전** | 서버·클라이언트 배포판에 사전 파일 동봉 |

> 브라우저가 HTML을 빠르게 받는 이유 중 하나가 이것이다.
> `<!DOCTYPE html>` 같은 문자열을 매번 보내지 않고 **"내장 사전 몇 번"** 으로 가리킨다.

---

## 6. 종합

| 질문 | 답 |
|---|---|
| 압축 대상 파일에서 패턴을 뽑나 | ❌ **아니다.** 같은 종류의 **다른 샘플**에서 뽑는다 |
| 대상 자신으로 뽑으면 안 되나 | ⚠️ 되지만 **사전을 동봉해야 해서** 이득이 거의 없다 (19.9% → 18.6%) |
| 왜 이득이 사라지나 | 사전 내용이 압축본에도 들어 있어 **같은 정보를 두 번 보내는 것** |
| 진짜 이득의 출처는 | ✅ **"사전이 이미 저쪽에 있다"** — 7.4%p가 전부 여기서 나옴 |
| 사전 비용을 세면 손해인가 | ❌ 918건 기준 19.9%로 여전히 유리. **손익분기 182건** |
| 소량만 압축한다면 | ❌ 10~100건이면 **명백한 손해.** 사전 쓰지 말 것 |
| 사전은 언제 만드나 | 서비스 시작 전에 한 번. 포맷 바뀌면 재학습 + 버전 관리 |

### 한 문장

> **사전이 공짜인 이유는 잘 만들어서가 아니라, 미리 가 있어서다.**
> **그래서 "압축 대상을 읽어서 만든다"는 순간 공짜가 아니게 되고, 이득의 대부분이 사라진다.**
> **사전은 압축 기술이 아니라 배포 인프라의 일부로 다뤄야 한다.**

## 부록 — 자기 데이터로 확인하는 법

```bash
# ⚠️ 반드시 학습셋과 평가셋을 분리할 것 (안 그러면 결과가 부풀려진다)
ls samples/ | shuf > all.txt
head -n $(( $(wc -l < all.txt) / 2 )) all.txt > train.txt
tail -n +$(( $(wc -l < all.txt) / 2 + 1 )) all.txt > test.txt

zstd --train $(sed 's|^|samples/|' train.txt) -o my.dict --maxdict=32768

# 평가는 학습에 안 쓴 것으로만
for f in $(sed 's|^|samples/|' test.txt); do
  zstd -19 -c    "$f" | wc -c   # 사전 없음
  zstd -19 -D my.dict -c "$f" | wc -c   # 사전 사용
done
```

손익분기 = `사전크기 ÷ (건당 절약 바이트)`. 이 값보다 적게 압축할 거면 사전을 쓰지 않는 게 낫다.

> **⚠️ 보정 ([11번](11-거대한-사전.md), 2026-08-27):** 이 문서는 사전 크기를 **32KB로 고정**하고 손익분기만 구했다.
> 사전 크기까지 같이 최적화하면 결과가 달라진다 — 로그 레코드 188건 기준, 사전 포함 최적은 **4KB(29.8%)** 이지 32KB(61.9%)가 아니다.
> **사전 크기는 고정 상수가 아니라 압축할 건수에 따라 같이 정해야 하는 변수다.** 건수가 적을수록 사전은 더 작아야 한다.

전체 스크립트는 세션 스크래치패드의 `honest.py`.

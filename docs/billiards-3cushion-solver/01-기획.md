## 1. 원안을 7개로 쪼개고 각각 판정

| # | 원안 요구 | 이미 있나 | 판정 |
|:-:|---|---|---|
| 1 | 포지션 → 해법 도출 | ✅ 3ball(브루트포스 솔버), Bricole(에이밍 계산) | **차별점 없음** |
| 2 | 파이브앤하프·플러스·플러스투 데모 플레이 | ✅ Bricole 8개 시스템, 3ball 학습 페이지 | **차별점 없음** |
| 3 | **팁 단위 회전 시 1~8쿠션 포인트** | ❌ 없음 | ⭐ **차별점** |
| 4 | 스쿼트·커브 계산 (밀어치기/그냥치기) | ❌ **없음 (실사용 확인)** | ⭐ **차별점** |
| 5 | 게임처럼 플레이 | ✅ 3ball, 각종 당구 게임 | **차별점 없음, 오히려 레드오션** |
| 6 | 해법 선 그리기 | ✅ 양쪽 다 궤적 다이어그램 | **차별점 없음** |
| 7 | AI 연결 | ❌ 3ball은 **명시적으로 ML 미사용** | **재검토 필요** (→ [02-설계](02-설계.md) 5절) |

### ⚠️ 2026-08-30 갱신 — 실사용 결과로 판정이 바뀌었다

사용자가 3ball을 직접 쳐 보고 내린 진단:

> **"내가 보통 치는 것과는 완전 다르다.** 스쿼트랑 커브가 계산에 없고, 나무 큐냐 카본 큐냐도 다르고,
> 두께 조절도 잘 안 보이고 그냥 각도만 맞춘 것 같다. **회전의 가중치가 안 맞고, 스트로크 타입에 따라서도 안 된다.**"

**미점유 항목이 1개가 아니라 최소 5개다:**

| 결손 | 성격 |
|---|---|
| 스쿼트·커브 미계산 | 물리 모델 누락 |
| 큐 개인화(피벗 길이) 없음 | 장비 파라미터 누락 |
| **두께가 입력 축에 없음** (각도만) | 입력 축 자체가 없음 |
| 회전 가중치(감쇠·전이) 부실 | 물리 모델 부실 |
| 스트로크 타입 미반영 | 입력 축 누락 |

> **정정: 경쟁 서비스는 같은 *화면*을 만들었지 같은 *모델*을 만들지 않았다.**
> 그리고 이 5개는 **UI를 고쳐서 되는 게 아니라 물리 엔진을 다시 짜야 하는 것들**이다 — 그만큼 따라오기 어렵다.

상세 사양: **[06-입력-파라미터-모델.md](06-입력-파라미터-모델.md)**

## 2. 재정의 — "해답기"가 아니라 "감도 엔진"

### 원안 3번이 왜 다른가

경쟁 서비스가 답하는 질문: **"어떻게 쳐야 하나?"** → 궤적 하나를 그린다.
원안 3번이 답하는 질문: **"당점을 1팁 더 주면 어디가 어떻게 바뀌나?"** → 궤적의 **변화율**을 준다.

```
[해답기]   포지션 ──▶ 궤적 1개                    "이렇게 치세요"
[감도엔진] 포지션 ──▶ 팁 0~4, 두께, 속도별
                     1~8쿠션 도달점 표/밴드        "1팁 = 3쿠션 4포인트"
```

**왜 이게 더 유용한가:**

| 이유 | 설명 |
|---|---|
| **테이블에서 쓸 수 있다** | 경기 중에 폰을 보며 칠 수 없다. 궤적 하나는 못 외우지만 **"1팁 = 4포인트"는 외워진다** |
| **실패를 진단한다** | 빗나갔을 때 "얼마나, 어느 방향으로" 틀렸는지로 **당점을 몇 팁 고칠지**가 나온다 |
| **시스템의 유효 범위를 준다** | 다이아몬드 시스템은 특정 당점·속도에서만 맞는다. 감도를 보면 **시스템이 깨지는 구간**이 보인다 |

### 핵심 가설

> **다이아몬드 시스템은 물리의 근사치다. 시스템 계산과 실제 물리는 반드시 어긋난다.**
> **팔릴 만한 제품은 답을 주는 쪽이 아니라, 그 괴리를 수치로 보여주는 쪽이다.**

이건 **검증 가능한 가설**이다. 당구장에서 배치 몇 개로 오차를 재면 몇 시간 안에 참·거짓이 갈린다.
→ [README](README.md) 다음 액션 3번.

## 3. 만들 것 / 안 만들 것

### 만든다

| 기능 | 근거 |
|---|---|
| **팁·두께·속도 감도표** (1~8쿠션 도달 포인트) | 원안 3번. 유일한 차별점 |
| **시스템 계산 ↔ 물리 시뮬 괴리 표시** | 핵심 가설. 다른 데 없음 |
| **괴리의 원인 분해** (스쿼트 / 커브 / 쿠션 반발 / 테이블 보정) | 원안 4번. "왜 틀렸나"에 답함 |
| **테이블 캘리브레이션** | 시스템의 전제인 보정값을 사용자 테이블에 맞춤 (Bricole도 함 → 필수 기능) |
| 궤적 렌더링 | 위 기능의 표시 수단으로만. 그 자체가 상품은 아님 |

### 안 만든다

| 기능 | 이유 |
|---|---|
| **게임 플레이 (원안 5번)** | 당구 게임 시장은 이미 포화. 리텐션 장치로도 무료 3ball이 있음. **여기에 개발력을 쓰면 차별점 0** |
| **범용 물리 엔진 자체 개발** | [tailuge/billiards](https://github.com/tailuge/billiards), [pooltool](https://ekiefl.github.io/2021/03/25/pooltool-start/) 오픈소스 존재. **바퀴 재발명 금지** |
| **카메라 실시간 인식** | 3ball이 이미 사진 정렬 제공. 초기엔 **수동 배치**로 충분 |
| **4구·포켓볼 확장** | 3쿠션 시스템이 핵심. 넓히면 정체성이 사라짐 |

> **"게임처럼 쳐도 되고"를 뺀 이유:** 원안에서 유일하게 **레드오션이면서 개발비가 가장 큰** 항목이다.
> v0에서 이걸 빼면 개발 범위가 절반 이하가 된다.

## 4. v0 최소 형태

```
입력: 공 3개를 도면에 드래그 (수동)
   ↓
① 시스템 계산     파이브앤하프 / 플러스 / 플러스투 중 적용 가능한 것을 골라 숫자를 보여줌
   ↓             "수구수 50 − 3쿠션수 20 = 1쿠션수 30"
② 물리 시뮬       같은 배치를 당점·속도별로 시뮬 → 실제 도달점
   ↓
③ 괴리 표시       "시스템 30 vs 물리 32 (+2)  ← 스쿼트 1.4 / 커브 0.6"
   ↓
④ 감도표          팁 0~4 × 1~8쿠션 도달 포인트 격자
```

**④가 상품이고 ①②③은 근거다.** 순서를 뒤집으면 경쟁 서비스와 같아진다.

## 5. 검증 가능성 — 이 아이디어의 구조적 강점

[프롬프트 팩 06번](../prompt-pack/06-카테고리-확장.md)에서 세운 기준을 그대로 적용한다.

| 기준 | 3쿠션 해법기 | 비고 |
|---|:-:|---|
| **자체 검증 가능성** | ⭐⭐⭐ | 당구대에서 쳐 보면 즉시 판명. 정답이 객관적 |
| 검증 비용 | ⭐⭐⭐ | 당구장 시간당 요금 수준 |
| 피드백 속도 | ⭐⭐⭐ | 초 단위 |
| 빈도 | ⭐⭐ | 동호인은 주 1~3회 침 (여행 연 1~2회보다 훨씬 나음) |
| B2B 가능성 | ⭐ | 당구장·코치 대상 여지는 있으나 약함 |
| **시장 크기** | ⭐ | **깔때기가 매우 좁다** → [03-시장분석](03-시장분석.md) |
| 경쟁 | ⭐⭐ | 서비스는 2개 있으나 **물리 모델에 결손 5개 확인** (2026-08-30 갱신) |

> 프롬프트 팩에서 여행이 최하위였던 이유는 "빈도 1점 + B2B 2점"이었다.
> 3쿠션은 **빈도는 개선되지만 시장 크기와 경쟁에서 더 나쁘다.**

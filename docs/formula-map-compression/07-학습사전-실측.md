# 07. 수식 10만 개의 현실판 — 학습 사전 실측

> **질문:** 수식 10만 개가 각기 다른 배열의 숫자를 산출하고, 그중 30%가 일치하고,
> 적어도 20개 숫자를 생산하고, 거기에 반복 구간 제거까지 더하면 어떨까?
>
> **답:** 산술 수식으로는 안 되지만(계산·실측 모두), **수식 10만 개를 데이터에서 뽑아내면 된다.**
> 그리고 그 효과는 **gzip 대비 69.3% 추가 절감**으로 실측됐다.

측정일: 2026-08-26

---

## 1. 먼저 — 가정대로 계산했을 때

원안의 가정을 전부 그대로 받아들이고 산수만 해보자.

```
수식 10만 개 → 번호 log₂(100,000) ≈ 17비트
토큰 = [플래그1][번호17][길이8] = 26비트 = 3.25바이트
가정: 30%가 적중, 토큰 하나가 20바이트 커버

수식 담당분 : 0.3N ÷ 20개 × 3.25바이트 = 0.049N
나머지 70%  : LZ77이 gzip 수준(9.7%)으로 처리 = 0.068N
──────────────────────────────────────────────
합계 = 0.117N  →  11.7%

gzip 단독 = 9.7%
```

### **가정을 전부 들어줘도 gzip보다 나쁘다.**

이유는 [06번](06-가변길이-실제구현.md)의 B안 내역에 이미 있었다.

| 파일 | 등차·상수 수식 커버 | 참조(LZ77) 커버 | 선택 비율 |
|---|---:|---:|---:|
| `cloud-init.log` | 193 바이트 | 145,940 바이트 | **756 : 1** |

**수식이 커버하려는 규칙적 구간은 LZ77이 가장 잘하는 구간과 겹친다.** 둘을 같이 주면 매 위치에서 경쟁하는데, 인코더가 이득이 큰 쪽을 고르면 756:1로 참조가 이긴다. 수식은 더해지는 게 아니라 **밀려난다.**

> 즉 "수식 + 반복 제거"는 두 효과가 합산되지 않는다. **대부분 같은 데이터를 놓고 다투기 때문이다.**

---

## 2. 그렇다면 "10만 개"가 의미를 가지려면

수식 10만 개가 값을 가지려면, 그것들이 **실제로 자주 나오는 패턴**이어야 한다.
`1,2,3,4` 같은 산술 규칙이 아니라, **그 데이터에 진짜로 반복되는 바이트 나열** 말이다.

그런데 무엇이 자주 나오는지는 사람이 정할 수 없다. **데이터에서 뽑아야 한다.**

```
원안        : 수식 10만 개를 미리 정해 둔다        → 무엇을 넣을지 알 수 없음
현실판      : 샘플 데이터에서 빈출 패턴을 학습한다  → zstd --train
```

이건 [03번](03-실측-수식맵-검증.md) 6절에서 언급한 학습 사전이며, **원안의 "미리 공유된 수식 맵"과 구조가 완전히 동일하다.** 맵을 손으로 정하지 않고 데이터가 정한다는 것만 다르다.

---

## 3. 실측 — 조건 설정

학습 사전이 이기는 조건은 **작은 파일이 아주 많을 때**다. 큰 파일 하나면 LZ77이 파일 자체에서 이미 학습하므로 사전이 필요 없다.

그래서 실제 서비스 환경을 흉내 냈다.

| 항목 | 값 |
|---|---|
| 원본 | `cloud-init.log` |
| 레코드로 분할 | **307개** (평균 **476바이트**) — 로그 한 건, API 응답 한 건에 해당 |
| 학습셋 | 153개 (사전 훈련용) |
| **평가셋** | **154개** (학습에 쓰이지 않은 것만) |
| 평가셋 원본 | 73,333 바이트 |
| 학습된 사전 | **30,242 바이트** (양쪽이 미리 공유 → 전송량 미포함) |

> 평가는 **학습에 쓰이지 않은 레코드**로만 했다. 사전이 외운 걸 되뱉는 게 아니라
> 처음 보는 데이터에도 통하는지 확인하기 위해서다.

---

## 4. 결과

| 방식 | 크기 | 원본 대비 |
|---|---:|---:|
| 원본 (무압축) | 73,333 | 100.0% |
| gzip -9 (개별) | 38,289 | 52.2% |
| zstd -19 사전 없이 (개별) | 36,794 | 50.2% |
| **zstd -19 + 학습 사전 (개별)** | **11,762** | **16.0%** |

```
=> 사전 도입 효과 : 36,794 → 11,762 바이트  (68.0% 추가 절감)
=> gzip 대비      : 69.3% 더 작음
```

### 레코드 하나 기준

| | 크기 |
|---|---:|
| 원본 | 476 바이트 |
| gzip | 249 바이트 |
| **학습 사전** | **76 바이트** |

**원안이 목표한 30% 절감을 한참 넘어, 사전 없는 상태 대비 68%를 더 줄였다.**

---

## 5. 왜 이렇게 잘 되나

476바이트짜리 레코드 하나만 놓고 보면, LZ77은 참조할 **과거가 없다.** 파일이 시작하자마자 끝나기 때문이다.

```
큰 파일 하나        : LZ77이 파일 앞부분을 참조 → 사전 불필요
작은 레코드 수천 개  : 각 레코드가 독립 → 참조할 과거가 없음  ← 사전이 채워주는 자리
```

학습 사전 30KB에는 이 로그에 흔한 패턴들 — 타임스탬프 형식, 모듈명, 반복되는 구문 — 이 들어 있다. 각 레코드는 그 사전을 **자기 앞에 있는 과거처럼** 참조한다.

> **이것이 원안의 "미리 공유된 맵으로 많은 바이트를 커버한다"가 실제로 작동하는 형태다.**
> 맵의 내용이 산술 수식이 아니라 **실제 데이터에서 뽑은 바이트 패턴**이라는 것만 다르다.

---

## 6. 정직하게 짚을 한계

| 한계 | 설명 |
|---|---|
| 큰 파일 하나에는 무의미 | 로그 전체를 통째로 gzip하면 **9.7%**다. 사전판 16.0%보다 좋다 |
| 사전 배포가 필요 | 송·수신 양쪽이 같은 사전을 가져야 한다. 버전 관리 필요 |
| 데이터가 바뀌면 재학습 | 로그 포맷이 바뀌면 사전 효과가 떨어진다 |
| 사전당 도메인 하나 | 로그용 사전은 이미지에 쓸모없다 |

> **사전의 가치는 "gzip을 이기는 것"이 아니라 "작은 파일이라 잃어버린 문맥을 되돌려주는 것"이다.**
> 로그 전체를 한 덩어리로 보낼 수 있으면 사전은 필요 없다.
> 그런데 실제 시스템에서는 레코드를 하나씩 보내야 하는 경우가 아주 많다 —
> API 응답, 로그 전송, DB 행, 메시지 큐, IoT 패킷.

원안에서 출발해 7개 문서에 걸쳐 검증한 결과를 한 표로 정리하면:

| 시도 | 결과 | 문서 |
|---|---|---|
| 고정 수식 맵으로 범용 무손실 압축 | ❌ 개수 세기로 불가능 증명 | [01](01-타당성-검토.md) |
| 수식으로 임의 데이터 표현 | ⚠️ 가능하지만 수식이 원본보다 큼 (288 vs 256바이트) | [04](04-수식은-항상-존재한다.md) |
| 수식을 많이 만들기 | ❌ 커버리지↑ = 번호 길이↑, 정확히 상쇄 | [04](04-수식은-항상-존재한다.md) |
| 고정 길이 10바이트 커버 | ❌ 등차수열 실측 0.0% | [05](05-수식-하나가-10바이트.md) |
| 가변 길이 탐욕 매칭 | ⚠️ 설계는 옳음. 산술 수식만으론 로그가 100.2%로 커짐 | [06](06-가변길이-실제구현.md) |
| **+ "앞에 나온 것 참조" 수식** | ✅ 100.2% → **12.8%** | [06](06-가변길이-실제구현.md) |
| **+ 데이터에서 학습한 사전** | ✅✅ 작은 레코드에서 gzip 대비 **69.3% 절감** | **이 문서** |

### 한 문장

> **원안의 직관 — "미리 공유된 맵의 번호 하나로 많은 바이트를 커버한다" — 은 처음부터 옳았다.**
> **틀린 것은 맵의 내용을 산술 수식으로 채우려 한 것뿐이다.**
> **맵을 데이터가 채우게 하면, 원안이 기대한 효과가 실제로 나온다.**

## 8. 다음 액션

이 결과는 **본인 데이터에 그대로 적용 가능하다.**

```bash
# 1. 같은 종류의 작은 파일들을 모은다 (수백~수천 개)
#    예: API 응답 JSON, 로그 레코드, 센서 패킷, 게임 세이브

# 2. 절반으로 사전을 학습
zstd --train samples/* -o my.dict --maxdict=110000

# 3. 나머지 절반으로 효과 측정 (학습에 안 쓴 것으로!)
zstd -19 test.json -o without.zst
zstd -19 -D my.dict test.json -o with.zst
ls -l without.zst with.zst
```

| | |
|---|---|
| 소요 시간 | 반나절 |
| 필요한 것 | 같은 종류의 작은 파일 샘플 |
| 기대 효과 | 이번 실측 기준 **사전 없는 대비 68% 추가 절감** |
| 실패 신호 | 개선이 10% 미만이면 그 데이터엔 공통 패턴이 없는 것 |

전체 스크립트는 세션 스크래치패드의 `dicttest.py`.

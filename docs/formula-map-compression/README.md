# 수식 맵 압축 (Formula Map Compression)

> 비트 시퀀스를 생성하는 수식들에 번호를 매겨 두고, **맵 번호 하나로 많은 바이트를 대체**하는 새로운 압축 방식.

## 원안

1. 비트를 연속 생성하는 **수식**들을 미리 정해 둔다
2. 수식마다 번호를 매긴 **수식 맵**을 만든다 (비트맵처럼)
3. 데이터를 **맵 번호 하나**로 대체해 전송한다
4. 순서는 바꿔도 되고, 256바이트를 배열처럼 다뤄도 된다
5. → 스트리밍 영상의 초반 256/512바이트가 수식 몇 개로 끝난다

---

## 결론 요약

### ❌ 범용 무손실 압축기로는 불가능하다

이건 구현·최적화·수식 선택으로 우회되는 문제가 아니라 **개수 세기(counting)** 로 증명되는 문제다.

| 근거 | 요지 |
|---|---|
| **커버리지** | 256바이트의 경우의 수는 10^616. 수식을 43억 개 준비해도 커버율 **10^-607** |
| **비둘기집 원리** | 길이 n 미만 출력은 2^n−1가지뿐 → 2^n개 입력을 담을 수 없다. 어떤 입력은 **반드시 커진다** |
| **반복 적용** | 모든 입력이 1비트라도 줄면, 반복해서 모든 파일을 1비트로 만들 수 있다 → 모순 |
| **재배열 비용** | 256개 재배열 방법을 지정하는 데만 `log₂(256!)` ≈ **210바이트** 소요 |
| **탐색 불가** | 짧은 수식이 존재해도 찾는 것은 콜모고로프 복잡도 = **계산 불가능** |

> **10초 자가진단법:** 새 압축 아이디어가 떠오르면 "모든 입력에 대해 줄어드나?"를 묻는다.
> **그렇다면 그 아이디어는 틀렸다.** 예외 없다.

**1분 실증:**
```bash
head -c 10000000 /dev/urandom > random.bin
gzip -9 -k random.bin
ls -l random.bin random.bin.gz    # .gz가 더 크다
```

### ✅ 그런데 직관 자체는 틀리지 않았다

원안의 "수식 맵"에는 이미 정식 명칭이 있다 — **모델**이다. 그리고 "압축 = 모델링"이라는 관점은 **정확히 옳다.** 부호화(산술 부호화)는 이미 이론적 최적에 도달했고, 남은 개선 여지는 전부 모델 쪽에 있다.

틀린 것은 방향이 아니라 **"모든 데이터를 커버해야 한다"는 요구**였다. 이것만 풀면 원안의 구조는 실제로 작동하며, 이미 여러 분야에서 쓰이고 있다.

| 실제 기술 | 원안과의 관계 |
|---|---|
| **VQ / 코드북 / LZ 사전** | "번호 하나가 여러 바이트 대체"를 문자 그대로 구현. 단 맵을 **학습**함 |
| **절차적 생성** (데모신) | 96KB에 3D 게임 전체. "작은 시드 → 많은 바이트"의 순수형 |
| **신경망 예측 + 산술 부호화** | **모델 가중치 = 수식 맵.** 원안에 가장 충실한 현대적 구현 |
| **손실 생성 코덱** | 스트리밍 영상 아이디어의 진짜 답. 비트가 아니라 **지각**을 복원 |

## 핵심 교훈

> **압축은 "모든 것을 줄이는 기술"이 아니라 "무엇을 포기할지 고르는 기술"이다.**
>
> 무손실 압축기는 *드문 데이터가 커지는 것*을 포기하고,
> 손실 압축기는 *지각되지 않는 정보*를 포기한다.
> 원안은 아무것도 포기하지 않으려 했고, 그래서 막혔다.

또 하나, 실패하는 압축 아이디어의 가장 흔한 공통점:

> **절약분은 세고 설명 비용(사이드 인포메이션)은 안 센다.**
> "순서를 바꿔도 된다"가 여기 해당한다 — 바꾸는 건 자유지만, **어떻게 바꿨는지 알려주는 비용**이 210바이트다.

# 프롬프트 팩 (Prompt Pack)

> 미리 만들어 둔 프롬프트 + 결과를 HTML 산출물로 뽑아주는 서비스.
> **"2주 걸리던 걸 10분에."**

| 항목 | 내용 |
|---|---|
| 등록일 | 2026-08-26 |
| 상태 | 아이디어 (검증 전) |
| 첫 버티컬 | 해외 자유여행 일정 설계 (일본) |
| 한 줄 요약 | 도메인별로 검증된 프롬프트 체인을 상품화해, 입력 몇 개만 받고 완성된 일정표·예약 체크리스트를 HTML로 내보내는 서비스 |

---

## 출발점 — 실제 겪은 문제 (삿포로 여행)

직접 삿포로 자유여행 일정을 ChatGPT로 짰고, **2주가 걸렸다.**

짜야 했던 것:
- 마지막 밤을 **노보리베츠**로 잡는 동선 설계 (삿포로 → 노보리베츠 → 신치토세공항)
- 노보리베츠 **송영버스** 예약 (온천 호텔 셔틀)
- 온천 → **공항버스** 예약 및 시간 맞추기 (체크아웃 시각 ↔ 버스 출발 ↔ 탑승 수속 역산)
- 둘째 날 **비에이 데일리투어** 예약

### 왜 2주나 걸렸나

| 원인 | 설명 |
|---|---|
| 컨텍스트 재설명 | 대화가 길어질수록 앞의 제약(항공편 시각, 인원, 예산)을 계속 다시 알려줘야 함 |
| 질문 순서를 모름 | "숙박 도시 순서 → 구간 교통 → 예약 시점" 순으로 물어야 하는데, 처음엔 그 순서를 모름 |
| 교통 연결 검증 누락 | LLM이 짜준 일정이 버스 막차·운행 요일·예약 마감을 안 따져서 실제로는 불가능한 경우 |
| 산출물이 안 남음 | 결론이 채팅 스크롤에 흩어져 있어, 정작 예약할 때 다시 뒤져야 함 |

**핵심 통찰:** 문제는 모델 성능이 아니라 **프롬프트의 순서·제약조건·검증 단계를 사용자가 직접 발명해야 한다는 것**. 그 발명 비용이 2주다. 그리고 그 발명은 한 번만 하면 재사용된다 → **상품이 된다.**

## 해결 방식

```
[사용자 입력 폼]              [프롬프트 체인 실행]           [산출물]
날짜 / 인원 / 예산      →   ① 제약 정규화              →   HTML 일정표
도착·출발 항공편             ② 숙박 도시 골격 설계          예약 체크리스트 (D-30/D-14/D-3)
이동 선호(렌트/대중교통)      ③ 구간 교통 연결 검증          구간별 이동 카드
꼭 가고 싶은 곳              ④ 예약 액션 리스트 생성        인쇄/오프라인용 페이지
                            ⑤ HTML 렌더                   공유 링크
```

사용자는 프롬프트를 쓰지 않는다. **이미 만들어진 팩을 고르고, 폼을 채우고, 결과를 받는다.**

## 현재 열려 있는 질문

1. **판매 단위** — 팩 단건 판매인가, 구독인가, 크레딧인가? (→ 04번 문서에서 비교)
2. **첫 버티컬을 여행으로 고정할 것인가** — 여행은 검증이 쉽지만 재구매 주기가 길다 (연 1~2회).
3. **환각 리스크를 어디까지 감당할 것인가** — 버스 시간표가 틀리면 여행을 망친다. 출처 강제 + "직접 확인" 표기로 충분한가, 아니면 실데이터 연동이 필수인가?

> 위 3개는 아직 미결이며, 각 문서에서 가정을 명시하고 진행했다.

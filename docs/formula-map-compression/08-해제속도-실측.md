# 08. 사전이 커지면 해제가 느려지나 — 실측

> **질문:** 사전에 저장된 패턴 데이터가 너무 많아지면 결국 빨리 못 풀지 않나?
> 나는 **압축 시간은 오래 걸려도 빨리 풀리게** 하려던 것인데.
>
> **답 1:** 그 설계 목표는 옳고, **LZ77/zstd가 원래 그렇게 생긴 구조**다. 압축:해제 = **121배** 비대칭으로 실측됐다.
> **답 2:** 사전이 커져도 **해제는 안 느려진다.** 오히려 **34% 빨라졌다.**
> **답 3:** 다만 사전이 커질수록 좋은 건 아니다 — **압축률**에서 역효과가 실측됐다.

측정일: 2026-08-26 / 대상: idea-aws (t4g.small, ARM 2 vCPU)

---

## 1. 왜 사전 크기가 해제 속도에 영향을 주지 않는가

압축과 해제는 **하는 일이 완전히 다르다.** 이게 핵심이다.

### 압축 — 탐색한다 (비쌈)

```
현재 위치에서:
  "앞의 수십만 바이트 중 지금과 가장 길게 일치하는 곳이 어디지?"
  → 해시 테이블 조회, 후보 수십 개 비교, 최장 매치 선택
  → 사전이 크면 탐색 공간이 커진다 → 느려진다  ✔ 여기서만 느려짐
```

### 해제 — 시킨 대로 복사한다 (쌈)

```
토큰을 읽는다: [거리 1700] [길이 40]
  → 1700바이트 뒤로 가서 40바이트 복사. 끝.
  → 탐색 없음. 판단 없음. 사실상 memcpy.
```

> **해제기는 "어디서 복사할지" 이미 답을 받아서 시작한다. 찾을 필요가 없다.**
> 그래서 해제 시간은 **출력 크기에만 비례**하고, 사전 크기와는 무관하다.

사전은 압축 창(window) 앞에 **미리 올려두는 것**일 뿐이다. 30KB든 1MB든 배열 인덱스 접근이라 O(1)이고, 로드는 **프로세스당 한 번**이면 이후 수천 번의 해제에 재사용된다.

---

## 2. 실험 A — 압축 레벨을 올리면 해제도 느려지나

대상: `words` 4,953,598 바이트

| 레벨 | 압축 크기 | **압축 시간** | **해제 시간** | 압축 속도 | 해제 속도 |
|---|---:|---:|---:|---:|---:|
| `-1` | 1,758,459 | **34 ms** | **15 ms** | 144 MB/s | 326 MB/s |
| `-9` | 1,465,670 | **223 ms** | **20 ms** | 22 MB/s | 251 MB/s |
| `-19` | 1,289,705 | **2,667 ms** | **22 ms** | 2 MB/s | 226 MB/s |

### 읽는 법

```
압축 시간 : 34ms → 2,667ms    (78배 느려짐)
해제 시간 : 15ms →    22ms    (거의 그대로)
```

> **레벨 19에서 압축은 2,667ms, 해제는 22ms — 121배 비대칭이다.**

**원안이 원한 "압축은 오래 걸려도 해제는 빨리"가 정확히 이것이다.** 새로 설계할 필요 없이 이미 그렇게 동작한다. 레벨을 올려서 압축에 시간을 쏟아도 해제 비용은 거의 그대로다.

이유는 1절 그대로다. 레벨을 올린다는 건 **압축기가 더 오래 탐색한다**는 뜻이고, 해제기는 그 탐색 결과를 받아쓰기만 한다.

---

## 3. 실험 B — 사전이 커지면 해제가 느려지나

대상: 1,836개 레코드, 합계 898,344 바이트 (평균 489바이트)

| 사전 크기 | 압축 결과 | 원본 대비 | **해제 시간** | **해제 속도** |
|---|---:|---:|---:|---:|
| 사전 없음 | 449,556 | 50.0% | **26 ms** | 35.1 MB/s |
| 4KB 사전 | 157,398 | 17.5% | **20 ms** | 45.2 MB/s |
| 32KB 사전 | 105,576 | **11.8%** | **19 ms** | 46.3 MB/s |
| 63KB 사전 | 114,768 | 12.8% | **19 ms** | **47.0 MB/s** |

### 결과 1 — 사전을 키워도 해제는 안 느려진다

```
4KB → 63KB (16배 증가)
해제 시간 : 20ms → 19ms   (변화 없음)
```

### 결과 2 — 오히려 빨라진다

```
사전 없음 : 26 ms  (35.1 MB/s)
사전 사용 : 19 ms  (47.0 MB/s)   ← 34% 더 빠름
```

**이유:** 사전을 쓰면 압축 결과가 449,556 → 105,576바이트로 줄어든다. **읽어야 할 데이터가 4분의 1이 되니 해제가 더 빨라진다.** 사전은 해제 비용을 늘리는 게 아니라 **줄인다.**

> **압축률이 좋아지면 해제도 빨라진다** — 디스크·네트워크에서 읽을 양이 줄고, 처리할 토큰 수도 줄기 때문이다.

---

## 4. 그런데 원안의 걱정에 맞는 부분이 있다

*"패턴 데이터가 많아지면"* 이라는 우려는 **속도가 아니라 압축률**에서 실제로 나타났다.

| 사전 크기 | 원본 대비 |
|---|---:|
| 4KB | 17.5% |
| **32KB** | **11.8%** ← 최적 |
| 63KB | 12.8% ← **나빠짐** |

**32KB에서 최적이고, 63KB로 키우니 오히려 나빠졌다.**

### 왜 나빠지나

| 원인 | 설명 |
|---|---|
| 참조 거리가 길어짐 | 사전이 크면 먼 곳을 가리켜야 해서 **거리 필드 비트 수가 늘어난다** |
| 희석 | 학습 데이터가 한정적인데 사전만 키우면 **드물게 쓰이는 패턴이 섞여 들어간다** |
| 학습량 부족 | 사전 크기가 학습 샘플 대비 과하면 과적합된 조각이 들어간다 |

> **사전은 무조건 클수록 좋은 게 아니다. 데이터마다 최적점이 있고, 그건 측정으로 찾아야 한다.**
> 이번 데이터에서는 32KB였다. 원안의 직관("너무 많아지면 문제")은 **압축률 축에서 맞았다.**

---

## 5. 종합

| 질문 | 답 |
|---|---|
| 사전이 커지면 해제가 느려지나 | ❌ **아니다.** 4KB→63KB에도 20ms→19ms |
| 오히려 어떻게 되나 | ✅ 사전 없을 때보다 **34% 빨라짐** (압축 결과가 작아서) |
| 왜 안 느려지나 | 해제는 **탐색이 없다.** "거리 D에서 L바이트 복사" 지시를 받아 실행할 뿐 |
| 압축은 오래, 해제는 빨리 — 가능한가 | ✅ **이미 그렇다.** 레벨 19에서 압축 2,667ms vs 해제 22ms (**121배**) |
| 그럼 사전은 크게 만들수록 좋나 | ❌ **아니다.** 이번 데이터에선 **32KB가 최적**, 63KB는 오히려 나빠짐 |
| 원안의 걱정은 틀렸나 | ⚠️ **속도 축에서는 기우, 압축률 축에서는 실재한다** |

### 한 문장

> **"압축은 느려도 해제는 빠르게"는 새로 설계할 목표가 아니라 LZ77 계열이 이미 달성해 둔 성질이다.**
> **사전의 비용은 시간이 아니라 메모리이고, 진짜 관리해야 할 것은 크기가 아니라 최적점이다.**

---

## 6. 실무 지침

| 상황 | 권고 |
|---|---|
| 한 번 압축해서 여러 번 배포 | `zstd -19` 또는 `--ultra -22`. 압축 시간은 신경 쓸 필요 없음 |
| 사전 크기 결정 | **여러 크기로 만들어 측정.** 무작정 키우지 말 것 (4KB/16KB/32KB/110KB 비교) |
| 해제 성능이 중요 | 사전을 쓰면 **오히려 유리하다.** 읽을 바이트가 줄어듦 |
| 사전 배포 | 프로세스 시작 시 한 번 로드해 재사용. 버전 번호를 붙여 관리 |

```bash
# 사전 크기별로 만들어 최적점 찾기
for kb in 4 16 32 110; do
  zstd --train samples/* -o d$kb.dict --maxdict=$((kb*1024)) -q
  echo -n "${kb}KB: "
  zstd -19 -D d$kb.dict -c test.bin | wc -c
done
```

전체 벤치마크 스크립트는 세션 스크래치패드의 `speedtest.py`.

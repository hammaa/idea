# 02. 설계

## 1. 팩 자료구조

하나의 팩은 3개 부분으로 구성된다.

```
Pack
├── input_schema      : 사용자에게 받을 필드 정의 (폼 자동 생성)
├── chain[]           : 순차 실행되는 프롬프트 단계들
└── output_template   : 최종 HTML 렌더 템플릿
```

### input_schema 예 — 일본 자유여행 팩

| 필드 | 타입 | 필수 | 비고 |
|---|---|:-:|---|
| `destination` | enum | ✓ | 홋카이도 / 간사이 / 규슈 … |
| `date_range` | date range | ✓ | |
| `party` | object | ✓ | 인원, 연령대, 유아 동반 여부 |
| `arrival_flight` | object | ✓ | 공항, 도착 시각 ← **동선 설계의 시작점** |
| `departure_flight` | object | ✓ | 공항, 출발 시각 ← **역산의 기준점** |
| `budget_tier` | enum | ✓ | 절약 / 보통 / 여유 |
| `mobility` | enum | ✓ | 대중교통 / 렌트카 / 혼합 |
| `must_visit` | text[] | | "비에이", "노보리베츠 온천" |
| `constraints` | text | | "마지막 밤은 온천에서 자고 싶다" |

> 삿포로 케이스가 알려준 것: **귀국 항공편 시각과 마지막 밤 숙소 위치가 일정 전체를 결정한다.** 이 두 개를 필수 입력으로 앞에 두는 것이 설계의 핵심.

## 2. 프롬프트 체인 (5단계)

기존에 사용자가 대화로 헤매며 발견해야 했던 순서를, 고정된 파이프라인으로 박제한다.

### ① 제약 정규화 (Normalize)

입력을 구조화된 제약 목록으로 변환.

```
출력: {
  hard_constraints: [
    "8/29 19:40 신치토세 출발편 → 17:40까지 공항 도착 필요",
    "마지막 밤 숙소는 온천 지역"
  ],
  soft_preferences: ["비에이 방문 희망"],
  derived: ["실질 여행일 = 4일 (도착일 반나절 제외)"]
}
```

**왜 필요한가:** 사용자가 "저녁 비행기예요"라고 하면 LLM이 이걸 계속 잊는다. 명시적 제약 객체로 뽑아 매 단계 프롬프트에 재주입한다.

### ② 숙박 도시 골격 (Skeleton)

날짜별로 **어느 도시에서 자는가**만 결정. 관광지는 아직 정하지 않는다.

```
Day 1: 삿포로   (도착 늦음 → 이동 최소화)
Day 2: 삿포로   (비에이 데일리투어 — 삿포로 출발/복귀)
Day 3: 삿포로
Day 4: 노보리베츠 (온천 1박)
Day 5: → 공항  (온천에서 공항버스 직행)
```

**왜 이 단계를 분리하나:** 관광지와 숙박을 동시에 정하면 LLM이 물리적으로 불가능한 동선을 만든다. 골격을 먼저 확정하고 잠가야 한다.

### ③ 구간 교통 연결 검증 (Verify) ← **가장 중요한 단계**

골격의 각 이동 구간에 대해 다음을 강제 점검한다.

| 점검 항목 | 삿포로 케이스에서의 실제 함정 |
|---|---|
| 운행 요일/시즌 | 데일리투어가 특정 요일만 운행 |
| 예약 필요 여부 / 마감 시점 | 온천 호텔 **송영버스는 사전 예약 필수** |
| 첫차·막차 | 온천 → 공항버스 편수가 적음 |
| 소요시간 + 버퍼 | 체크아웃 시각 ↔ 버스 출발 ↔ 수속 마감 역산 |
| 좌석/정원 제한 | 데일리투어 만석 위험 |

이 단계의 출력은 **"검증 결과 + 근거 링크 + 신뢰도"** 이며, 불확실하면 반드시 `⚠️ 직접 확인 필요`로 표기한다. (→ 5절 환각 대응)

### ④ 예약 액션 리스트 (Actions)

"무엇을, 언제, 어디서 예약하는가"를 시점 역산으로 생성.

```
D-45  항공권 (가격 상승 전)
D-30  온천 료칸 — 인기 날짜는 조기 마감
D-14  ⚠️ 노보리베츠 송영버스 — 료칸 예약 후 별도 신청
D-14  비에이 데일리투어
D-7   온천 → 신치토세 공항버스
D-3   최종 시각 재확인 (운휴 공지 체크)
```

**이게 진짜 상품이다.** 일정표는 블로그에도 있지만, "언제 무엇을 예약해야 하는지"를 내 날짜 기준으로 정리해주는 건 없다.

### ⑤ HTML 산출물 렌더 (Render)

①~④의 구조화된 결과를 템플릿에 주입. LLM에게 자유 HTML을 짜게 하지 않고, **고정 템플릿 + 데이터 바인딩**으로 품질을 고정한다.

## 3. 산출물 스펙

한 번 생성하면 아래를 모두 받는다.

| 산출물 | 내용 | 형식 |
|---|---|---|
| **일정표** | 날짜별 타임라인, 숙박지, 이동 구간 | HTML (반응형) |
| **예약 체크리스트** | D-day 역산 액션, 체크박스, 예약처 링크 | HTML (인쇄 가능) |
| **구간 이동 카드** | 출발/도착 시각, 수단, 소요, 예약번호 기입란 | HTML (모바일 우선) |
| **⚠️ 확인 필요 목록** | LLM이 확신 못 한 항목만 모아둔 페이지 | HTML |
| 오프라인 사본 | 위 전체를 단일 HTML로 (해외 데이터 없어도 열림) | 단일 파일 |

설계 원칙:
- **모바일 우선** — 현지에서 폰으로 본다
- **오프라인 동작** — 외부 리소스 의존 없이 단일 HTML
- **인쇄 가능** — 체크리스트는 종이로 쓰는 사람이 있다
- **공유 링크** — 동행자에게 보내는 게 자연스러운 확산 경로

## 4. 시스템 아키텍처 (v1)

```
[웹 프론트]
   폼 (input_schema로 자동 생성)
        │
        ▼
[오케스트레이터]  ── 체인 단계별 순차 호출, 제약 객체 재주입
        │            중간 결과 저장 (재실행/부분 수정 지원)
        ▼
[Claude API]      ── 단계별 프롬프트, 구조화 출력 강제
        │
        ▼
[렌더러]          ── 고정 HTML 템플릿 + 데이터 바인딩
        │
        ▼
[스토리지]        ── 산출물 저장, 공유 링크 발급, 재다운로드
```

기술 선택 (초안):
- LLM: Claude API — 단계별로 구조화 출력(스키마 강제)이 필요하고, 긴 제약 컨텍스트를 유지해야 함
- 단계별 모델 분리: ①②④는 가벼운 모델, ③(검증)은 상위 모델 — 원가 최적화 여지 (→ [04-수익구조.md](04-수익구조.md))
- 프론트/백: 단순 웹앱 (v0는 아예 개발 없음)

## 5. 환각 대응 — 이 서비스의 최대 리스크

> **버스 시간표가 틀리면 여행을 망친다.** 이건 "답이 좀 아쉬움" 수준의 문제가 아니라 신뢰가 즉사하는 문제다.

### 3단 방어

| 단계 | 방식 |
|---|---|
| 1. 신뢰도 등급 강제 | 모든 교통/예약 정보에 `확정 / 추정 / 확인필요` 라벨을 붙이도록 스키마에 강제 |
| 2. 출처 링크 필수 | 근거 URL 없으면 자동으로 `확인필요`로 강등 |
| 3. 별도 페이지 분리 | `⚠️ 확인 필요 목록`을 산출물 맨 앞에 배치 — 숨기지 않고 전면에 |

### 포지셔닝으로 방어

"완벽한 일정을 드립니다"가 아니라
**"2주 걸릴 설계를 10분에 끝내드립니다. 최종 확인할 항목은 따로 정리해드립니다."**

→ 과대약속을 하지 않는 것이 오히려 신뢰를 만든다. 실제로 사용자는 어차피 예약처 사이트에 들어간다.

### 장기 대응 (v2+)

- 시간표/운행일 실데이터 연동 (교통사 공식 페이지 크롤 또는 API)
- 사용자 피드백 루프: "실제로 이 버스 있었나요?" → 오답 수집 → 프롬프트/데이터 보정
- 오답 데이터베이스가 쌓이면 그 자체가 **진입장벽**이 된다

## 6. 프롬프트 자산을 어떻게 지키나

프롬프트는 복사되기 쉽다. 방어선은 프롬프트 자체가 아니다.

| 방어선 | 설명 |
|---|---|
| 체인 + 검증 로직 | 프롬프트 한 줄이 아니라 5단계 파이프라인과 실패 케이스 처리 |
| 산출물 템플릿 | HTML 품질은 별도의 디자인 자산 |
| 오답 DB | 사용자 피드백으로만 쌓이는 데이터 |
| 브랜드/사례 | "삿포로 2주 → 10분" 스토리 자체 |

→ 결론: **프롬프트를 파는 게 아니라 결과물과 신뢰를 판다.** 프롬프트 텍스트 판매(v0의 임시 형태)에 오래 머물면 안 되는 이유.

# 01. 타당성 검토 — 왜 범용 무손실로는 불가능한가

> 이 문서의 주장은 의견이 아니라 **증명**이다. 반례가 존재할 수 없는 종류의 결론이므로,
> 구현 방식·수식 선택·최적화로 우회되지 않는다.

---

## 0. 제안 정리

원안을 정확히 옮기면 이렇다.

1. 비트 시퀀스를 연속으로 생성해내는 **수식**들을 미리 정해 둔다
2. 수식들에 번호를 매긴 **수식 맵**을 만든다 (비트맵처럼)
3. 데이터를 보낼 때 **맵 번호 하나**로 많은 바이트를 대체한다
4. 순서는 바꿔도 되고, 256바이트를 배열처럼 다뤄도 된다

아래에서 각 단계를 차례로 검토한다.

---

## 1. 개수 세기 (Counting Argument)

### 1-1. 256바이트에 몇 가지 경우가 있나

```
256 바이트 = 2,048 비트
가능한 값의 수 = 2^2048 ≈ 10^616
```

감을 잡기 위한 비교:

| 대상 | 개수 |
|---|---|
| 관측 가능한 우주의 원자 수 | 약 10^80 |
| **256바이트 블록의 경우의 수** | **약 10^616** |

우주의 모든 원자를 각각 우주 하나로 바꾸는 걸 7번 반복해야 겨우 도달하는 수다.

### 1-2. 수식 맵의 커버리지

수식 맵의 번호를 `N`비트로 표현한다고 하자. 표현 가능한 번호는 `2^N`개다.

> **서로 다른 입력은 서로 다른 번호로 가야 한다.**
> (같은 번호가 되면 압축 해제 시 어느 쪽인지 알 수 없다 = 무손실이 아니다)

따라서 모든 256바이트 블록을 커버하려면:

```
2^N ≥ 2^2048   →   N ≥ 2048 비트 = 256 바이트
```

**맵 번호가 원본과 같은 크기가 된다. 압축률 0%.**

### 1-3. 수식을 "정해 둔다"고 했을 때

원안은 수식 집합을 고정한다. 넉넉하게 잡아 **43억 개(2^32)**의 수식을 준비했다고 하자.

```
커버 가능한 블록 수 :  2^32       ≈ 4.3 × 10^9
전체 블록 수       :  2^2048     ≈ 1.0 × 10^616

커버율 = 4.3×10^9 / 10^616 ≈ 10^-607
```

임의의 256바이트 블록이 이 맵에 존재할 확률은 **10^-607**이다. 사실상 0이 아니라, 실질적으로 0이다.

수식을 1조 개로 늘려도 `10^12 / 10^616`이라 달라지는 게 없다. **지수가 상대가 안 된다.**

---

## 2. 비둘기집 원리 — 일반형 증명

위는 256바이트에 대한 계산이지만, 결론은 모든 길이에 대해 성립한다.

> **정리.** 어떤 무손실 압축기도 모든 입력을 짧게 만들 수 없다.

**증명.**

길이 `n`비트인 입력은 `2^n`가지다.
길이가 `n`비트 **미만**인 출력은 전부 합쳐도:

```
2^0 + 2^1 + ... + 2^(n-1) = 2^n − 1 가지
```

`2^n`개를 `2^n − 1`개에 일대일로 넣을 수 없다. 최소 두 입력이 같은 출력을 갖게 되고, 그 순간 복원이 불가능하다. ∎

**따라서 어떤 압축기든 반드시 이렇다:**

| | |
|---|---|
| 어떤 입력은 짧아진다 | ← 우리가 원하는 것 |
| **다른 어떤 입력은 반드시 길어진다** | ← 피할 수 없는 대가 |

압축은 "정보를 줄이는 기술"이 아니라 **"흔한 것을 짧게, 드문 것을 길게 바꾸는 교환"**이다. 총량은 절대 줄지 않는다.

---

## 3. 반복 적용 논증 (가장 직관적인 반박)

만약 제안한 압축기가 **모든** 입력을 단 1비트라도 줄인다고 하자.

```
1 GB 파일
 → 압축 → 1 GB − 1 bit
 → 압축 → 1 GB − 2 bit
 → 압축 → ...
 → 압축 → 1 bit
```

출력도 데이터이므로 다시 입력으로 넣을 수 있다. 반복하면 **모든 파일이 1비트가 된다.**
그러면 세상의 모든 파일이 `0` 또는 `1` 두 개뿐이어야 한다. 명백한 모순이다.

> 이 논증이 유용한 이유: 새 압축 아이디어가 떠올랐을 때 **10초 만에 자가 검증**할 수 있다.
> "모든 입력에 대해 줄어드나?" → 그렇다면 틀린 것이다.

---

## 4. "순서를 바꿔도 된다"에 대하여

원안의 *"꼭 순서대로 할 필요 없어, 256을 배열처럼 만들어서"* 부분을 따로 본다.

재배열 자체는 자유지만, **어떤 순서로 바꿨는지를 받는 쪽에 알려줘야 한다.** 그 비용이 얼마인가.

256개 항목의 순열 개수는 `256!`이고, 이를 지정하려면:

```
log₂(256!) ≈ 1,684 비트 ≈ 210 바이트
```

**256바이트를 재배열하는 방법을 설명하는 데만 210바이트가 든다.**

원본이 256바이트인데 순서 정보가 210바이트라면, 남는 46바이트 안에 내용까지 담아야 한다. 재배열은 공짜가 아니며, 오히려 대부분의 예산을 잡아먹는다.

> 일반화: **"어떻게 복원할지"를 알려주는 정보(사이드 인포메이션)도 데이터다.**
> 새 압축 아이디어가 실패하는 가장 흔한 지점이 이것 — 절약분은 세고 설명 비용은 안 세는 것.

---

## 5. 설령 존재해도 찾을 수 없다

논의를 양보해서, 어떤 특정 256바이트 블록에 대해 짧은 수식이 **우연히 존재**한다고 하자. 그래도 두 개의 벽이 남는다.

### 5-1. 탐색 비용

그 수식을 찾으려면 수식 공간을 뒤져야 한다. 맵이 2^32개면 최악의 경우 43억 번 평가한다. 블록 하나당. 1GB 파일이면 블록이 400만 개다.

압축 시간이 실용 범위를 벗어난다.

### 5-2. 콜모고로프 복잡도 (이론적 벽)

"이 데이터를 만들어내는 가장 짧은 프로그램의 길이"를 **콜모고로프 복잡도**라 한다. 원안이 찾으려는 것이 정확히 이것이다.

여기에 두 가지 알려진 사실이 있다.

| 사실 | 의미 |
|---|---|
| **계산 불가능(uncomputable)** | 최단 수식을 찾아주는 알고리즘은 존재할 수 없다 (정지 문제로 환원) |
| **대부분의 문자열은 압축 불가능** | 길이 n인 문자열 중 n−k 비트 미만으로 표현 가능한 것은 2^(−k) 비율뿐 |

두 번째를 구체화하면: 임의의 데이터 중 **10비트라도 줄어드는 것은 1024개 중 1개 미만**이다.

## 6. "그러면 기존 압축기는 어떻게 되는 건가"

여기서 중요한 전환이 있다. **기존 압축기도 위 정리를 위반하지 않는다.**

zip/gzip이 텍스트를 70% 줄이는 이유는 마법이 아니라, **실제 데이터가 균등분포가 아니기 때문**이다.

- 한국어 텍스트에서 `한` 다음에 `국`이 올 확률은 균등분포의 예측보다 훨씬 높다
- 사진에서 옆 픽셀은 대개 비슷한 색이다
- 실행 파일에는 같은 명령 패턴이 반복된다

압축기는 이 **치우침(bias)** 을 먹고 산다. 그리고 그 대가로, 치우침이 없는 데이터(예: 난수, 이미 압축된 파일)는 **오히려 커진다.**

### 직접 확인하는 법

터미널에서 1분이면 검증된다.

```bash
head -c 10000000 /dev/urandom > random.bin
gzip -9 -k random.bin
ls -l random.bin random.bin.gz    # .gz 쪽이 더 크다
```

난수는 치우침이 없으므로 압축되지 않고, 헤더만큼 늘어난다. **모든 압축기가 이 시험을 통과하지 못한다.** 통과한다고 주장하는 압축기는 예외 없이 오류이거나 사기다.

### 섀넌 한계

주어진 확률 모델 아래에서 도달 가능한 최소 크기는 **엔트로피**로 정해져 있고, 산술 부호화(arithmetic coding)는 이미 그 한계에 임의로 가깝게 도달한다.

> **부호화(encoding) 측면은 이미 끝난 문제다.**

## 7. 스트리밍 동영상에 대하여

원안의 *"초반 256, 512바이트가 수식 몇 개로 끝난다"* 부분.

| 지점 | 사실 |
|---|---|
| 동영상 파일의 초반 수백 바이트 | 컨테이너 헤더(코덱 정보·해상도·인덱스). 이미 조밀하며 압축 여지가 거의 없다 |
| 영상 본체 | H.264/HEVC/AV1이 이미 **움직임 예측 + 변환 + 엔트로피 부호화**로 원본 대비 100배 이상 줄이고 있다 |
| 남은 여지 | 무손실로는 거의 없음. **손실 허용 시에는 크게 있음** ← 여기가 진짜 기회 |

즉 스트리밍에서 원안이 노린 효과는 **무손실을 포기하는 순간 실제로 가능해진다.** 다음 문서의 주제다.

## 8. 결론

| 질문 | 답 |
|---|---|
| 범용 무손실 압축기로 가능한가 | ❌ **불가능.** 개수 세기로 증명됨 (1·2절) |
| 수식을 더 잘 고르면 되나 | ❌ 지수 격차라 무의미 (1-3절: 커버율 10^-607) |
| 재배열로 이득을 볼 수 있나 | ❌ 순서 설명 비용이 210바이트 (4절) |
| 존재하는 경우만 쓰면 되나 | ⚠️ 탐색 비용 + 계산 불가능성 (5절) |
| **아이디어가 완전히 틀렸나** | ❌ **아니다.** 틀린 것은 "무손실 + 범용"이라는 틀뿐 |

> **핵심 통찰이 틀린 게 아니라, 적용 조건이 틀렸다.**
> "작은 시드로 많은 바이트를 생성한다"는 발상 자체는 실제로 작동하는 기법이며,

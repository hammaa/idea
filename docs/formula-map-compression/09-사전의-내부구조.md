# 09. 사전 안의 "바이트 패턴"은 실제로 어떻게 생겼나

> **질문:** 바이트 패턴은 어떻게 구성되는데? 실제 패턴을 정확히 매칭하는 거야? 뭘로?
>
> **답:** 사전은 **표도 목록도 아니고 그냥 바이트 덩어리 하나**다.
> 매칭은 **정확히 일치(exact match)** 이고, 방법은 **LZ77의 `[거리][길이]` 그대로**다.
> 실제로 사전을 열어서 확인했다.

측정일: 2026-08-26

---

## 1. 사전 파일의 구조 — 실제로 열어본 결과

```
전체 크기   : 23,859 바이트
매직 넘버   : 0xEC30A437   (zstd 사전 표식)
사전 ID     : 364308806    (압축본이 '어느 사전인지' 가리키는 번호)
앞부분 130B : 엔트로피 테이블(허프만/FSE) + 반복 오프셋 힌트
나머지 전부 : ★ 그냥 바이트 덩어리 23,729바이트 — 이게 패턴 본체
```

| 구역 | 크기 | 내용 |
|---|---:|---|
| 헤더 | 8 바이트 | 매직 넘버 + 사전 ID |
| 엔트로피 테이블 | ~120 바이트 | 미리 학습된 허프만/FSE 테이블 |
| **콘텐츠** | **23,729 바이트** | **패턴 본체 — 구조 없는 생바이트** |

### 여기가 핵심

> **"수식 10만 개"에 해당하는 것은 목록이 아니다. 항목도, 번호도, 구분자도 없다.**
> **그냥 바이트가 23,729개 이어져 있는 덩어리 하나다.**

### 읽는 법

- `2026-08-26 01:53:` — 이 로그의 타임스탬프 형식

**전부 이 로그에서 실제로 자주 등장한 조각들이다.**

그리고 중요한 특징:

| 관찰 | 의미 |
|---|---|
| 조각들이 **문장 중간에서 잘려 있다** (`that ma` `tches d`) | 의미 단위가 아니라 **바이트 빈도**로 뽑았다는 증거 |
| 조각 사이에 **구분자가 없다** | 개별 항목이 아니라 **하나의 연속된 덩어리** |
| 조각이 **겹쳐서 이어붙어 있다** | 공간을 아끼려고 최대한 압착 |

> **사전은 "패턴 목록"이 아니라 "가상의 과거"다.**
> 압축기는 이 덩어리를 **파일 앞에 이미 지나간 데이터인 것처럼** 취급한다.


### 답 — "정확히 매칭하는 거야? 뭘로?"

| 질문 | 답 |
|---|---|
| 정확히 일치인가 | ✅ **완전히 정확한 바이트 일치.** 유사·근사 매칭 없음 |
| 무엇으로 매칭하나 | **LZ77과 똑같이** `[거리][길이]` 토큰 |
| 거리는 무엇을 가리키나 | 파일 안이 아니라 **사전 안의 위치** (예: 9697번) |
| 매칭 단위 | 고정 없음. **4바이트부터 수백 바이트까지 가변** |
| 못 맞추면 | 그 바이트는 **원본 그대로** 전송 (리터럴) |

**즉 [06번](06-가변길이-실제구현.md)에서 만든 B안의 "참조 수식"과 완전히 같은 메커니즘이다.**
다른 점은 참조 대상이 "파일 앞부분"이 아니라 **"미리 공유된 사전"** 이라는 것뿐이다.

```
파일 내 참조 : [거리 1700][길이 40]  → 1700바이트 앞으로
사전 참조    : [거리 9697][길이 35]  → 사전의 9697번 위치로   ← 유일한 차이
```

## 4. 그럼 "10만 개"는 어디에 있나

원안의 "수식 10만 개"에 대응하는 것은 **사전 안의 위치 개수**다.

```
사전 콘텐츠 23,729 바이트
→ 시작 가능한 위치가 23,729개
→ 각 위치에서 길이 4~수백 바이트까지 가능
→ 사실상 수십만 가지 조합
```

**목록으로 세어 둔 게 아니라, 덩어리 하나에서 위치와 길이를 조합해 무한정 만들어낸다.**
이게 "10만 개를 어떻게 저장하나"라는 걱정이 필요 없는 이유다 — 저장하는 게 아니라 **주소로 지정**한다.

| | 원안 | 실제 |
|---|---|---|
| 저장 형태 | 수식 10만 개를 각각 저장 | **바이트 덩어리 하나** |
| 지정 방법 | 수식 번호 | **(위치, 길이) 쌍** |
| 표현 가능 수 | 10만 개 고정 | 위치×길이 조합 = **수십만 이상** |
| 크기 | 10만 개 × 항목 크기 | **23KB** |

## 5. 사전은 어떻게 만들어지나 (`zstd --train`)

zstd는 **COVER / fastCover** 계열 알고리즘을 쓴다. 대략 이렇게 동작한다.

```
1. 샘플 전체를 훑으며 짧은 조각(보통 8바이트 단위)의 등장 빈도를 센다
2. 후보 구간마다 점수를 매긴다
   점수 = (이 구간이 커버하는 샘플 수) × (커버 길이)
   단, 이미 뽑힌 구간과 겹치는 만큼은 점수에서 뺀다
3. 점수가 가장 높은 구간부터 탐욕적으로 선택
4. 선택된 구간들을 이어붙여 사전 콘텐츠를 만든다
   (자주 쓰이는 것을 뒤쪽에 배치 — 거리가 짧아져 인코딩이 유리)
5. 앞부분에 엔트로피 테이블을 붙인다
```

- 2번의 "겹치는 만큼 감점"이 있어서 **비슷한 조각이 중복 수록되지 않는다**
- 조각이 문장 중간에서 잘리는 이유도 여기 있다 — **의미가 아니라 커버리지로 뽑기 때문**
- [08번](08-해제속도-실측.md)에서 32KB가 63KB보다 좋았던 이유도 여기 있다:
  점수가 낮은 구간까지 억지로 채우면 **거리만 길어지고 쓸모는 없다**

## 6. 종합

| 질문 | 답 |
|---|---|
| 바이트 패턴은 어떻게 구성되나 | **구조 없는 바이트 덩어리 하나.** 목록도 표도 구분자도 없음 |
| 안에 뭐가 들어있나 | 학습 샘플에서 자주 나온 **생바이트 조각들** (문장 중간에서 잘림) |
| 정확히 매칭하나 | ✅ **완전 정확 일치.** 유사 매칭 없음 |
| 무엇으로 매칭하나 | **LZ77의 `[거리][길이]` 토큰.** 거리가 사전 내부를 가리킴 |
| 매칭 단위는 | 가변 — 실측에서 **4~35바이트**, 이론상 수백까지 |
| 못 맞추면 | 원본 그대로 전송 (실측: 496바이트 중 72바이트) |
| "10만 개"는 어디에 | 저장하지 않는다. **위치×길이 조합으로 생성** |

### 한 문장

> **사전은 패턴 사전이 아니라 "미리 붙여둔 가짜 과거"다.**
> **압축기는 그것을 이미 읽은 데이터처럼 취급하고, 평소처럼 `[거리][길이]`로 가리킬 뿐이다.**
> **새로운 메커니즘은 하나도 없다 — 참조할 과거를 미리 만들어줬을 뿐이다.**

```bash

xxd my.dict | head -40          # 헤더 + 엔트로피 테이블
strings my.dict | head -40      # ★ 자주 나오는 조각들이 그대로 보인다
```

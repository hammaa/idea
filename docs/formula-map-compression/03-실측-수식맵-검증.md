# 03. 실측 — "수식 1000개로 30%"는 가능한가

> **질문 재정의:** "모든 데이터를 압축한다"가 아니라 **"수식 1000개로 실제 데이터의 30%를 줄인다"**.
> 이건 [01번](01-타당성-검토.md)의 개수 세기 논증에 걸리지 않는다. **완전히 다른, 정당한 주장이다.**
> 수학 문제가 아니라 **측정 문제**이므로, 실제로 측정했다.

측정일: 2026-08-26 / 대상: idea-aws 서버의 실제 파일들

---

## 1. 먼저 — RLE(연속 문자 줄이기)의 정확한 위치

원안에서 언급한 *"hexa로 해서 연속되는 문자를 줄이는 것"* 은 **RLE(Run-Length Encoding)** 이다.

```
AAAAAAAAAAAA  (12바이트)  →  A×12  (2바이트)
```

### RLE가 이기는 곳 / 지는 곳

| 상황 | 결과 |
|---|---|
| 팩스, 단색 아이콘, 스캔 문서 | ✅ 매우 효과적 (흰 여백이 길게 반복) |
| 0으로 채워진 패딩 영역 | ✅ 효과적 |
| 자연어 텍스트 | ❌ **오히려 커진다.** 같은 글자가 2번 연속인 경우조차 드묾 |
| 사진 | ❌ 노이즈 때문에 연속이 안 생김 |
| 이미 압축된 파일 | ❌ 커진다 |

### RLE는 이미 흡수되었다

RLE는 **LZ77의 특수한 경우**다. 현대 압축기(gzip/zstd/xz)는 LZ77 계열을 쓰는데, 이건 "바로 앞 글자의 반복"만이 아니라 **파일 안 어디에 나왔던 문자열이든 참조**한다.

```
RLE   : 직전 문자의 반복만 잡음
LZ77  : "1,700바이트 전에 나온 40바이트와 같음" 같은 참조도 잡음  ← RLE를 포함
```

따라서 **RLE로 잡히는 건 gzip이 이미 전부 잡고 있다.** 새로 만들 이유가 없다.

## 2. 손익분기 계산 — 몇 %를 맞춰야 30%가 나오나

수식 1000개면 인덱스는 10비트(`2^10 = 1024`)다. 256바이트 블록 단위로 다음처럼 인코딩한다고 하자.

```
적중 : [플래그 1비트][수식번호 10비트]        =    11 비트
실패 : [플래그 1비트][원본 2048비트]          = 2,049 비트
```

적중률을 `p`라 하면 블록당 기대 크기는:

```
E = 11p + 2049(1−p) = 2049 − 2038p
원본 = 2048 비트

30% 절감 → E = 1433.6
2049 − 2038p = 1433.6  →  p ≈ 0.302
```

### **결론: 30%를 줄이려면 실제 블록의 30%가 수식에 정확히 맞아야 한다.**

여기서 중요한 관찰이 하나 나온다.

> **인덱스 비용(11비트)은 사실상 공짜다.** 2048비트에 비하면 0.5%에 불과하다.
> 따라서 이 방식의 성패는 **오로지 적중률 하나**로 결정된다.
> 수식을 1000개로 하든 100만 개로 하든(20비트) 결과는 거의 안 변한다.

**즉 진짜 질문은 이것이다: "실제 파일의 256바이트 블록 중 몇 %가 단순 수식으로 표현되는가?"**

---

## 3. 실측

### 방법

실제 파일을 256바이트 블록으로 자르고, 각 블록이 아래 세 가지 수식 중 하나로 **정확히** 표현되는지 판정했다.

| 수식 | 정의 |
|---|---|
| 상수 | 모든 바이트가 동일 (= RLE로 잡힘) |
| 등차수열 | 인접 바이트 차이가 일정 (= delta 필터로 잡힘) |
| 짧은 주기 | 주기 16 이하의 반복 패턴 |

> 실제로는 이 3종이 "수식 1000개"보다 훨씬 넓은 범위를 커버한다.
> 상수만 해도 256가지, 등차수열은 `256 × 256` = 65,536가지가 자동 포함되기 때문이다.
> **즉 아래 수치는 수식 1000개짜리 맵보다 유리하게 잡은 상한선이다.**

### 결과

| 파일 | 크기 | 블록 수 | 수식 적중 | **적중률** | gzip | zstd | xz |
|---|---:|---:|---:|---:|---:|---:|---:|
| `python3.9` (실행파일) | 200,080 | 781 | 751 | **96.2%** | 1.9% | 1.6% | 1.6% |
| `libc.so.6` | 2,318,424 | 9,056 | 366 | **4.0%** | 38.8% | 33.9% | 28.8% |
| `bash` | 1,500,240 | 5,860 | 327 | **5.6%** | 45.8% | 41.5% | 35.9% |
| `libcrypto.so.3` | 5,307,720 | 20,733 | 288 | **1.4%** | 40.4% | 35.2% | 31.0% |
| `words` (영어 사전) | 4,953,598 | 19,349 | 0 | **0.0%** | 29.8% | 26.0% | 24.8% |
| `cloud-init.log` (로그) | 150,062 | 586 | 0 | **0.0%** | 9.7% | 8.5% | 8.6% |

*(gzip/zstd/xz 열은 압축 후 크기가 원본의 몇 %인지. 낮을수록 좋음)*

---

## 4. 결과 해석 — 결정적인 패턴

### 4-1. 텍스트·로그에서 적중률은 정확히 0%

`words`와 `cloud-init.log`에서 **적중 블록이 단 하나도 없다.** 반면 gzip은 로그를 **90.3%나 줄였다.**

> 수식 맵 방식으로는 이 파일들에서 **1바이트도 못 줄인다.** (오히려 플래그 비트만큼 커진다)
> gzip은 10분의 1로 만든다.

### 4-2. 적중률 96%가 나온 파일의 정체

`python3.9`만 96.2%로 튀었다. 내역을 열어보면:

```
zero  : 751 블록   ← 전부 0으로 채워진 블록
other :  30 블록
const :   0 블록   (0이 아닌 상수 블록은 없음)
```

**적중한 751개가 전부 `0x00` 블록이다.** 즉 이 파일은 대부분이 패딩이다.

그런데 **바로 그 데이터야말로 gzip이 가장 잘하는 것**이다. 실제 대결을 계산해 보면:

| 방식 | 결과 크기 | 원본 대비 |
|---|---:|---:|
| 수식 맵 (적중 751×11비트 + 실패 30×2049비트) | 8,716 바이트 | 4.4% |
| **gzip -9** | **3,802 바이트** | **1.9%** |

> **수식 맵이 가장 잘 통하는 최상의 조건에서조차 gzip이 2.3배 더 좋다.**

### 4-3. 한 문장 결론

> **수식이 맞아떨어지는 곳은 gzip이 이미 공짜로 처리하는 곳이고,**
> **gzip이 진짜 일하는 곳(텍스트·로그)에서는 수식 적중률이 0%다.**

두 방식은 같은 것을 놓고 경쟁하지 않는다. 수식 맵이 잘하는 영역은 **gzip이 잘하는 영역의 부분집합**이다.

---

## 5. 왜 고정 수식은 적응형 사전에 지는가

근본 이유는 **실제 데이터의 반복은 보편적이지 않고 파일마다 고유하기 때문**이다.

| | 고정 수식 맵 | 적응형 사전 (LZ77) |
|---|---|---|
| 사전 출처 | 미리 정한 1000개 | **그 파일 자체에서 실시간 생성** |
| `cloud-init.log`에서 잡는 것 | 없음 | `"2026-08-26 01:5"`, `"[DEBUG] util.py"` 등 그 로그에만 있는 반복 |
| 한계 | 예상한 패턴만 | 예상하지 못한 패턴도 |

로그 파일이 90% 줄어드는 이유는 타임스탬프 접두사와 모듈명이 수백 번 반복되기 때문인데, **이건 어떤 고정 수식으로도 미리 준비할 수 없다.** 그 파일을 읽어야만 알 수 있다.

## 6. 그런데 — 원안이 진짜로 통하는 지점이 있다

여기서 중요한 반전이 있다. **고정 사전(= 수식 맵)이 적응형을 이기는 조건이 실제로 존재한다.**

### 조건: 작은 파일이 아주 많을 때

적응형 사전은 **파일을 읽으면서 학습**한다. 그런데 파일이 500바이트면 학습할 시간이 없다. 사전이 준비되기도 전에 파일이 끝난다.

```
큰 파일 1개     →  적응형 승리 (파일이 스스로를 가르쳐 줌)
작은 파일 10만 개 →  고정 사전 승리 (학습할 틈이 없음)  ← 원안의 자리
```

### 이미 제품으로 존재한다

| 기술 | 내용 |
|---|---|
| **Brotli 내장 사전** | 웹에서 흔한 문자열(`<!DOCTYPE html>`, `function`, HTTP 헤더 등)을 담은 약 120KB 정적 사전을 **표준에 내장**. 모든 브라우저가 이미 갖고 있어 전송량에 포함되지 않는다 |
| **Zstd 학습 사전** (`zstd --train`) | 샘플 데이터로 사전을 **훈련**시켜 양쪽에 배포. 작은 JSON·로그·레코드에서 압축률이 크게 개선됨 |
| **xz `--delta` 필터** | "각 값 = 직전 값 + 차이"라는 **수식을 전처리로 적용**. 오디오·표 형식 데이터에서 효과가 큼 |
| **BCJ 필터** | 실행파일의 점프 주소를 상대값으로 변환하는 수식 전처리 |

> **원안의 "미리 공유된 수식 맵"은 이미 존재하며, 이름은 *정적 사전(static dictionary)* 또는 *필터*다.**
> 브라우저를 열 때마다 이미 쓰고 있다.

## 7. 실현 가능한 프로젝트 (수정)

[02번](02-대안-설계.md) 4절의 "안 1"을 이 실측 결과로 구체화하면 이렇다.

### 만들 것: 특정 워크로드용 학습 사전

새 압축 알고리즘을 만드는 게 아니라, **zstd 사전을 특정 데이터에 맞춰 훈련**시킨다.

```bash
# 1. 샘플 수집 (같은 종류의 작은 파일 수천 개)
# 2. 사전 훈련
zstd --train samples/* -o my.dict

# 3. 비교 측정
zstd -19 sample.json -o without.zst              # 사전 없이
zstd -19 -D my.dict sample.json -o with.zst      # 사전 사용
```

| 항목 | |
|---|---|
| 대상 후보 | 소형 JSON API 응답, 개별 로그 레코드, 게임 세이브, IoT 센서 패킷 |
| 기대 효과 | 작은 파일에서 **수십 % 개선 가능** (원안의 30% 목표와 정확히 같은 눈높이) |
| 소요 시간 | **반나절.** 개발이 아니라 측정 |
| 원안과의 관계 | "미리 공유된 맵으로 많은 바이트 커버" — **구조가 동일**. 다만 맵을 손으로 정하지 않고 데이터에서 학습 |

## 8. 종합 답변

| 질문 | 답 |
|---|---|
| "30%만 줄여도 좋지 않나?" | ✅ **목표로서는 완벽히 합리적이다.** 30%면 훌륭하다 |
| 수식 1000개로 30%가 되나? | ❌ 실측 적중률이 텍스트·로그 **0%**, 일반 바이너리 **1~6%**. 30%에 한참 못 미친다 |
| 인덱스를 늘리면 되나? | ❌ 인덱스 비용은 이미 공짜(0.5%). **적중률만이 변수다** |
| 최상의 조건에서는? | ❌ 적중률 96% 파일에서도 gzip이 **2.3배 더 좋았다** |
| 그럼 완전히 무의미한가? | ❌ **아니다.** 작은 파일이 많은 워크로드에서 정적 사전은 실제로 이긴다 |
| 무엇을 해야 하나 | ✅ **`zstd --train`으로 특정 워크로드 사전 훈련.** 반나절이면 30% 목표의 달성 여부를 실측할 수 있다 |

### 가장 중요한 교훈

> **비교 대상을 "무압축"이 아니라 "gzip"으로 잡아야 한다.**
>
> 원안의 30%는 *압축하지 않은 원본* 기준이었다. 그런데 로그 파일의 실제 기준선은 **이미 90% 줄어든 gzip 결과**다.
> 새 방식은 그 위에서 다시 30%를 줄여야 의미가 있다.

## 부록 — 재현 방법

측정 스크립트는 세션 스크래치패드에 있으며(`blockscan.py`), 핵심 로직은 다음과 같다.

```python
BLK = 256
def classify(b):
    if b.count(b[0]) == len(b):                    # 상수
        return "constant"
    d = (b[1] - b[0]) % 256                        # 등차수열
    if all((b[i+1] - b[i]) % 256 == d for i in range(len(b)-1)):
        return "arithmetic"
    for p in range(1, 17):                         # 짧은 주기
        if all(b[i] == b[i % p] for i in range(len(b))):
            return "periodic"
    return "none"
```

본인 데이터에 대해 돌려보면 그 데이터에서의 적중률을 바로 알 수 있다.
